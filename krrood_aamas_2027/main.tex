\begin{abstract}
Many robots and other autonomous agents are built on cognitive architectures, which organize perception, planning, control and learning into modules that share knowledge. We consider architectures whose modules are object-oriented programs. When such an agent represents its knowledge in an external formalism such as OWL or RDF to perform logical inference, the knowledge lives in a second representation, with assumptions of its own, that must be kept synchronized with the program. We present KRROOD, a framework in which the agent's object-oriented program is its knowledge base: classes and property descriptors form the terminology, live objects form the assertions, and property rules fire when facts are asserted. The Entity Query Language (EQL) queries the program with a formal, closed-world semantics. Its predicates and functions are the agent's own procedures, so reasoning is not limited to logical inference. Ontomatic compiles OWL~2~RL ontologies into such programs, with guarantees of soundness and, under conditions we identify, completeness for positive queries. ORMatic maps the same classes to a relational database that serves as the agent's long-term memory, and translates a subset of EQL to SQL. On the OWL2Bench benchmark, KRROOD's knowledge base equals the closure of an OWL~2~RL reasoner assertion by assertion, and its queries return the same answers. Its loading and query times lie within the range of established OWL and RDF systems: loading takes seconds, and queries take 1.7 times GraphDB's time in geometric mean.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Many robots and other autonomous agents are built on cognitive architectures, which organize perception, planning, control and learning into modules that share knowledge about the world and the task~\cite{langley2009cognitive,kotseruba2020cognitive}. In robotics, ontologies in the Web Ontology Language (OWL) are a common way to make this knowledge explicit, shareable and open to sound inference~\cite{olivares2019review,Tenorth2013,delgrande2024current}. We consider architectures whose modules are object-oriented programs, in which perception produces objects and planners and controllers manipulate them~\cite{beetz2025robot}. For a developer, the practical value of an OWL ontology depends on how well it integrates with the agent's \emph{application code}, the program that perceives, decides and acts~\cite{ledvinka2020comparison}.

Today this integration means maintaining two representations of the same world, the objects of the program and the individuals of the ontology, each with concerns of its own~\cite{davis1993knowledge}. OWL is designed for sound inference over knowledge that may be incomplete and assumes an open world, in which a missing fact is unknown, whereas programs and databases are designed for computing over data that they treat as complete~\cite{Reiter1978}; the two also treat names and inconsistencies differently~\cite{motik2009bridging}. The developer translates the program's state, invokes a reasoner on the exported copy and maps the results back, minding these differences. This is an object-ontological counterpart of the object-relational impedance mismatch~\cite{ireland2015exposing,ledvinka2020comparison}.

A second requirement comes from the agent itself. Reasoning in robotics goes beyond logical inference over stated facts: it calls procedures and combines knowledge of several modalities, such as images and other sensor data~\cite{beetz2018know}. Much of what a robot knows is computed from its own data: whether an object is on a table follows from the poses that perception estimates. KnowRob, a knowledge processing system for robots~\cite{Tenorth2013,beetz2018know}, therefore attaches procedures, called computables, to the predicates of its knowledge base. A knowledge representation for such agents has to let reasoning call the agent's own code.

This paper argues that this knowledge can instead be \emph{represented explicitly in the agent's object-oriented program}, so that the program itself becomes the knowledge base and its procedures take part in reasoning. We present \acf{krrood}, a Python framework built on this idea (Figure~\ref{fig:arch}). Classes and property descriptors form the TBox and live objects the ABox, and property rules fire when application code asserts a fact. A query language with a formal, closed-world semantics reasons over the objects directly, and its predicates and functions are ordinary Python callables, so reasoning in \ac{krrood} is not limited to logical inference. We compare it with OWL~2~RL reasoners to benchmark its reasoning, not because OWL~2~RL bounds what it can express. The argument applies to any object-oriented language; we use Python, common in robotics and machine learning, whose operator overloading and introspection allow a query language to be embedded in it. We make four contributions:

\begin{enumerate}
\item An object-oriented knowledge representation with a formal reading as a knowledge base, in which properties are first-class descriptors that carry their logical characteristics, multiple classification is handled by roles, and predicates are computed by the agent's own code (Section~\ref{sec:kr}).
\item The \acf{eql}, a query language embedded in Python, with a formal semantics that places it in known complexity classes, and in which class axioms and rules are ordinary query conditions (Section~\ref{sec:eql}).
\item Ontomatic, which compiles OWL~2~RL ontologies into such programs so that positive queries return only entailed answers and, under conditions we identify, all of them (Section~\ref{sec:ontomatic}).
\item ORMatic, which generates a relational schema from the same classes as the agent's long-term memory and translates a subset of \ac{eql} to SQL (Section~\ref{sec:ormatic}).
\end{enumerate}

We evaluate them on the OWL2Bench benchmark~\cite{singh2020owl2bench}, comparing answers, loading and reasoning time, memory use and query time with established OWL and RDF systems (Section~\ref{sec:experiments}). Source code, experiment scripts and the full formalization of \ac{eql} are provided as anonymized supplementary material.

\section{Related Work}
\label{sec:related-work}

\paragraph{Knowledge representations}
Knowledge is represented as RDF triples~\cite{rdf11concepts}, queried with SPARQL~\cite{sparql11query}; as OWL axioms over them, read under an open world~\cite{owl2overview,baader2003dlhandbook}, with profiles such as OWL~2~RL~\cite{motik2012owl2profiles}; as Datalog rules or relational tables, read under a closed world~\cite{AbiteboulHullVianu1995,Reiter1978}; and as classes and objects, on which \ac{krrood} builds; each form has commitments of its own~\cite{davis1993knowledge,brachman2004knowledge}.

\paragraph{Object-ontology mapping}
In the OWL API~\cite{horridge2011owl}, objects represent axioms and class expressions rather than domain entities. Jastor~\cite{szekely2009jastor}, the mapping of Kalyanpur et al.~\cite{kalyanpur2004automatic}, KOMMA~\cite{wenzel2010komma} and JOPA~\cite{ledvinka2016jopa} generate or annotate Java classes whose instances stand for individuals, while the ontology store remains the authoritative copy; Puleston et al.\ argue for hybrid models in which part of the knowledge stays in the ontology~\cite{puleston2008integrating}. In Python, Owlready2~\cite{lamy2017owlready} creates classes from an ontology at load time and stores individuals in a quadstore, and OWLAPY~\cite{baci2025owlapy} models OWL entities and axioms as Python constructs, as OWLOOP~\cite{buoncompagni2024owloop} does in Java. In all of these, the OWL ontology defines the program's classes, and an external reasoner's results are read back. \ac{krrood} reverses the direction: the classes of application code are the knowledge base, an OWL ontology is one way of generating them, and inference and queries run inside the program.

\paragraph{Reasoners and materialization}
OWL reasoners such as Pellet~\cite{sirin2007pellet}, HermiT~\cite{glimm2014hermit} and RacerPro~\cite{haarslev2012racerpro} decide entailment for expressive description logics. Rule-based systems such as RDFox~\cite{nenov2015rdfox} and GraphDB materialize the consequences of OWL~2~RL with Datalog-style rules, building on description logic programs~\cite{grosof2003description}. They operate on their own stores. \ac{krrood} materializes RL consequences in the objects of application code instead, property consequences at the time facts are asserted, and evaluates queries, including the predicates they call, under the closed-world reading that Motik et al.~\cite{motik2009bridging} and Tao et al.~\cite{tao2010integrity} give to the constraints that developers write in OWL.

\paragraph{Queries and rules in the host language}
LINQ integrates queries over objects, relations and XML into .NET languages~\cite{meijer2006linq}. pyDatalog~\cite{carbonnelle2020pydatalog} embeds Datalog in Python and queries attributes of Python objects, and ProbLog~\cite{dries2015problog2} embeds probabilistic logic programs. ErgoAI~\cite{kifer2018ergoai} offers object-oriented logic programming through F-logic~\cite{kifer1995flogic}, and KnowRob~\cite{Tenorth2013,beetz2018know} reasons in Prolog over a robot's OWL knowledge base, with computables that compute facts from the robot's data when a query needs them. All of these keep the terminology in a logic language, outside the application's classes. Production rule systems such as Drools~\cite{proctor2012drools} match rules against a working memory of host-language objects with the Rete algorithm~\cite{forgy1982rete}, but the rules are written in a rule language, and the program must insert its objects into the engine and report their changes. \ac{eql} combines the embedding of LINQ with a first-order query language and rules over the program's own objects, whose concepts, properties and predicates are classes related by inheritance; recursion, such as transitivity, is left to property descriptors.

\paragraph{Ontologies in agent programming}
In multi-agent systems, JADE maps agent-communication content to Java classes that correspond to the schemas of an ontology~\cite{bellifemine2007jade,caire2010jadeontology}. AgentSpeak-DL~\cite{moreira2006agentspeakdl} and JASDL~\cite{klapiscak2009jasdl} combine belief--desire--intention (BDI) agents with description-logic reasoning over their belief bases. Recent work finds that BDI frameworks lack support for ontological beliefs, inference and queries over them~\cite{burattini2025gap}, and maps triples to beliefs~\cite{longo2025t2b2t}. In JaCaMo~\cite{boissier2013jacamo}, the observable properties of artifacts, which are Java objects~\cite{ricci2011cartago}, are likewise mapped to the beliefs of agents, and the working memory of Soar~\cite{laird2012soar} is a graph of the architecture's own elements. \ac{krrood} addresses these needs in Python: the belief base is the program's objects, and inference and queries operate on it directly.

\section{Knowledge Representation in KRROOD}
\label{sec:kr}

In \ac{krrood}, the knowledge base of an agent is its object-oriented program. We use one running example throughout the paper: an assistant agent for a university whose knowledge comes from the OWL2Bench university ontology~\cite{singh2020owl2bench}. Its \emph{application code}, which for instance suggests courses to students, manipulates \texttt{Person}, \texttt{Student} and \texttt{Course} objects, which are also the individuals of its knowledge base.

\paragraph{Vocabulary}
A \ac{krrood} knowledge base is a pair $\mathcal{K}=(\mathcal{T},\mathcal{A})$. The TBox $\mathcal{T}$ consists of Python declarations of four kinds:
\begin{itemize}
  \item \emph{Concepts} are classes. Subsumption between named concepts is declared by inheritance, and \texttt{issubclass} computes its reflexive-transitive closure.
  \item \emph{Properties} (binary relations) are attributes. Each attribute is managed by a \emph{property descriptor}, a class whose position in the descriptor hierarchy encodes property subsumption (\texttt{IsCrazyAbout} $\sqsubseteq$ \texttt{Loves} $\sqsubseteq$ \texttt{Likes}) and whose \emph{mixins}~\cite{bracha1990mixin} (base classes that each add one behavior to the classes inheriting from them) encode property characteristics such as transitivity, symmetry, inverses and property chains.
  \item \emph{Axioms} that typing and inheritance cannot express, such as the definition of a class by a necessary and sufficient condition (\texttt{T20CricketFan} in Listing~\ref{lst:axiom}), are class methods that return an \ac{eql} condition (Section~\ref{sec:eql}) characterizing the members of the class. Because $\mathcal{K}$, like a relational database~\cite{reiter1984relational}, has a single interpretation, an axiom does not constrain models as in a description logic~\cite{baader2003dlhandbook}. It is a condition that can be checked, like an integrity constraint~\cite{motik2009bridging,tao2010integrity}, or used to classify individuals (Section~\ref{sec:ontomatic}).
  \item \emph{Predicates and symbolic functions} are Python callables that can appear as atoms of \ac{eql} conditions. They give reasoning direct access to the agent's own procedures, such as the reachability check of Listing~\ref{lst:agent}.
\end{itemize}
The ABox $\mathcal{A}$ consists of the live objects and their attribute values, which form the agent's \emph{working memory}. Listing~\ref{lst:kr} shows part of the running example. Its last statement attaches a descriptor to a class attribute: from then on, every read and write of \texttt{is\_crazy\_about} on a \texttt{Person} passes through \texttt{IsCrazyAbout}, which applies the property's rules.\footnote{Listings are simplified. They use the current version of \acs{krrood}; Ontomatic (Algorithm~\ref{alg:loading}) and the experiments use an earlier version, and the supplementary material contains both.}

\begin{lstlisting}[style=eql, caption={Part of the running example. Classes are concepts, attributes are properties, and descriptor classes carry property semantics.}, label={lst:kr}]
@dataclass(eq=False)
class Person(Thing):
    is_crazy_about: set[Interest]
@dataclass(eq=False)
class Student(Role[Person]):  # played by a Person
    takes_course: set[Course]
class Loves(Likes): ...
class IsCrazyAbout(Loves): ...  # sub-property
class IsPartOf(PropertyDescriptor, TransitiveProperty): ...
# IsCrazyAbout manages Person.is_crazy_about
Person.is_crazy_about = IsCrazyAbout(Person,
                                     "is_crazy_about")
\end{lstlisting}

\paragraph{Multiple classification through roles}
An OWL individual may belong to classes unrelated by subsumption, such as \texttt{Student} and \texttt{SportsFan}, but a Python object has a single most specific class, and multiple inheritance would need a class for every combination, fixed when the object is created. \ac{krrood} resolves this with the Role pattern~\cite{steimann2000roles,Guarino2004,boella2007roles}, whose implementations in Python have been compared~\cite{bassiouny2026roles}. In this paper ``role'' refers only to this pattern: a role is an object of its own class that refers to the entity playing it, its \emph{role taker}, and delegates to it reads of every attribute it does not declare itself (\texttt{Student} in Listing~\ref{lst:kr}). A student who is also a sports fan is one \texttt{Person} object with a \texttt{Student} role and a \texttt{SportsFan} role, so the individual keeps a single identity.

\paragraph{Interpretation}
$\mathcal{K}$ has a single interpretation $\mathcal{I}_{\mathcal{A}}$, which assigns a set of individuals to every concept and a set of pairs to every property. Objects and individuals do not correspond one to one, so we write $\mathit{ind}(o)$ for the individual that an object $o$ denotes: a role object denotes the individual of its role taker, an object created for an ontology individual denotes the individual named by its IRI, and every other object denotes an individual of its own. On data values, such as numbers and strings, $\mathit{ind}$ is the identity. With $O$ the set of objects in memory, a concept $C$ denotes $C^{\mathcal{I}}=\{\mathit{ind}(o)\mid o\in O \text{ is an instance of } C\}$. A property $P$ that manages attribute $p$ relates the individual of every object to the individual of every value of its attribute: $P^{\mathcal{I}}=\{(\mathit{ind}(o),\mathit{ind}(v))\mid o\in O,\ v \text{ is } o.p \text{ or an element of } o.p\}$. A predicate denotes the tuples for which its code returns true, and a symbolic function the function its code computes. Their extensions are not stored in $\mathcal{A}$ but computed when a query needs them, like the computables of KnowRob~\cite{Tenorth2013}. $\mathcal{K}$ is read under the assumptions of relational databases~\cite{Reiter1978,reiter1984relational}:
\begin{itemize}
  \item \emph{closed world}: a ground atom, such as $\texttt{Student}(\mathit{alice})$ or a predicate applied to values, is false unless $\mathcal{I}_{\mathcal{A}}$ makes it true, which for a predicate means that its code returns true, so nothing is unknown;
  \item \emph{domain closure}: there are no individuals other than those that objects denote;
  \item \emph{unique names}: two objects denote the same individual only if they carry the same IRI or one is a role of the other, directly or through further roles (in OWL2Bench, a \texttt{TeachingAssistant} role is played by a \texttt{Student} role, which is played by a \texttt{Person}).
\end{itemize}
These are the assumptions under which application code already treats its objects; Section~\ref{sec:ontomatic} reconciles them with OWL.

\paragraph{Reasoning inside the program}
Property descriptors apply the consequences of a fact when application code asserts it: assigning a value to an attribute triggers forward chaining over the descriptor's characteristics. For example, adding T20 cricket to \texttt{p.is\_crazy\_about} also adds it to \texttt{p.loves} and \texttt{p.likes}. Class membership is derived when knowledge is loaded (Section~\ref{sec:ontomatic}) or by rules on request (Section~\ref{sec:eql}). Every inferred fact records the rule and the facts that produced it, so conclusions can be explained. $\mathcal{K}$ is queried, and axioms are evaluated, with \ac{eql}.

\section{EQL: Querying the Program as a Knowledge Base}
\label{sec:eql}

\ac{eql} is a declarative query language embedded in Python. An \ac{eql} query is not a string passed to an external engine, as in SQL or SPARQL, but a Python expression built from symbolic variables, whose names and types the development environment can check, evaluated directly over live objects. This continues the idea of language-integrated queries~\cite{meijer2006linq}, adding first-order formulas, negation as failure, quantifiers, rules and user-defined predicates. The supplementary material contains the full formalization of its syntax, semantics and complexity.

\subsection{Syntax}
\label{ssec:eql_syntax}

\paragraph{Variables and terms}
A variable \texttt{x = variable(C, domain=D)} is a symbol ranging over the instances of class $C$ in a finite collection $D$. If $D$ is omitted, it is the set of all known instances of $C$. Because $D$ can be any collection computed by the program, a query can be restricted to the task-relevant part of the knowledge base. Terms are built from constants, variables, attribute access \texttt{t.a}, indexing \texttt{t.a[i]}, method calls \texttt{t.m($\bar t$)} and symbolic functions \texttt{f($\bar t$)}. Chains of attribute accesses replace the joins of relational query languages.

\paragraph{Atoms and formulas}
An atom is a predicate applied to terms, $p(\bar t)$, a comparison $t_1 \mathbin{\mathsf{op}} t_2$ with $\mathsf{op}\in\{=,\neq,<,\le,>,\ge,\in\}$, or a Boolean-valued term. Formulas are built by
\[
\varphi ::= \alpha \mid \varphi\wedge\varphi \mid \varphi\vee\varphi \mid \neg\varphi \mid \exists x\in D.\,\varphi \mid \forall x\in D.\,\varphi ,
\]
written as several arguments of \texttt{where}, \texttt{or\_}, \texttt{not\_}, \texttt{exists} and \texttt{for\_all}. The domain of a quantified variable may depend on outer variables. For example, \texttt{flat\_variable(s.takes\_course)} ranges over the courses of each student $s$.

\paragraph{Queries}
A query selects one or more variables, \texttt{entity(x)} or \texttt{set\_of(x, y)}, constrained by \texttt{.where($\varphi$)}, and is wrapped in a result quantifier. The result quantifier \texttt{an} accepts any number of answers, and \texttt{the} requires exactly one, following Russell's definite description~\cite{russell1905denoting}, and raises an error otherwise. Aggregates (\texttt{count}, \texttt{sum}, \texttt{max}, \dots) with \texttt{grouped\_by} and \texttt{having} correspond to the grouping operator of relational algebra~\cite{Klug1982}.

Listing~\ref{lst:q22} shows OWL2Bench query Q22, ``students who take a course taught by the dean of an organization'', in SPARQL and in \ac{eql}. Each triple pattern becomes an attribute chain or a membership atom: no join keys are written, and the only join is the membership atom. Here \texttt{s} ranges over a collection \texttt{students} computed by the program; in the benchmark, over all students.

\begin{lstlisting}[style=eql, caption={OWL2Bench query Q22 in SPARQL (top) and \acs{eql} (bottom).}, label={lst:q22}]
SELECT ?s ?c WHERE { ?s a :Student .
  ?o a :Organization . ?o :hasDean ?d .
  ?d :teachesCourse ?c . ?s :takesCourse ?c }
\end{lstlisting}
\vspace{-0.9\baselineskip}
\begin{lstlisting}[style=eql]
s = variable(Student, domain=students)
o = variable(Organization)
dean = flat_variable(o.has_dean)
c = flat_variable(dean.teaches_course)
q22 = an(set_of(s, c).where(contains(s.takes_course, c)))
\end{lstlisting}

\paragraph{Axioms and rules}
Since an axiom is a class method returning an \ac{eql} condition, it can be inspected, used as a constraint, or used as the body of a rule. Listing~\ref{lst:axiom} shows the OWL2Bench definition $\texttt{T20CricketFan}\equiv\exists\texttt{isCrazyAbout}.\{\texttt{T20Cricket}\}$ as an axiom, and a rule that derives a \texttt{T20CricketFan} role for every person satisfying it. In general, a rule \texttt{inference(H)($\bar k$)} derives an instance of class $H$ for each answer of its body. Like an object identifier created by a Skolem functor~\cite{hull1990ilog}, a derived object is identified by its class and its arguments. Evaluating the rule again, or another rule with the same class and arguments, returns the same object, so rule evaluation is idempotent. A rule is evaluated on request, like a query, and returns the derived objects.

\begin{lstlisting}[style=eql, caption={An OWL class definition as an axiom, used as the body of a classification rule.}, label={lst:axiom}]
@dataclass(eq=False)
class T20CricketFan(SportsFan):
    @classmethod
    def axiom(cls, p):
        return contains(p.is_crazy_about, T20_CRICKET)

p = variable(Person)
fan = inference(T20CricketFan)(role_taker=p)
fans = an(entity(fan).where(T20CricketFan.axiom(p)))
\end{lstlisting}

\paragraph{A step of the agent}
Listing~\ref{lst:agent} puts these pieces together in one step of the university assistant. Application code asserts an observed enrolment, which triggers the property rules, and an \ac{eql} query then suggests courses that the student does not take and whose rooms they can reach in the break after algebra. The reachability check is a predicate whose code searches the campus map for a shortest path, procedural knowledge the agent already has as code.

\begin{lstlisting}[style=eql, caption={A step of the assistant agent: assert an observation, then decide with a query that calls a domain procedure.}, label={lst:agent}]
@dataclass
class CanReachInTime(Predicate):
    start: Room
    goal: Room
    def __call__(self):  # shortest path on the campus map
        return walking_minutes(self.start, self.goal) <= BREAK

alice.takes_course.add(algebra)       # perceive
c = variable(Course, domain=offered)  # decide
suggestions = an(entity(c).where(
    not_(contains(alice.takes_course, c)),
    CanReachInTime(algebra.room, c.room)))
\end{lstlisting}

\subsection{Semantics}
\label{ssec:eql_semantics}

A query $Q(\bar x)\leftarrow\varphi(\bar x,\bar y)$ is evaluated in the single interpretation $\mathcal{I}_{\mathcal{A}}$ of Section~\ref{sec:kr}. Its answers are
\[
\mathit{ans}(Q,\mathcal{K}) = \{\theta(\bar x) \mid \mathcal{I}_{\mathcal{A}}\models \varphi\theta\},
\]
where $\theta$ ranges over the assignments of values from their domains to $\bar x$ and $\bar y$, and $\models$ is first-order satisfaction. Atoms are evaluated by computing their terms and, for predicates, calling them. Every variable ranges over a finite domain, which may depend on the values of outer variables, so every query is safe. Negation is negation as failure: $\neg\varphi\theta$ holds if and only if $\varphi\theta$ is not satisfied in $\mathcal{I}_{\mathcal{A}}$. Because $\mathcal{I}_{\mathcal{A}}$ is a single finite interpretation of ground facts, this is Reiter's closed-world assumption~\cite{Reiter1978}. As in SQL, answers are produced with bag semantics, and \texttt{distinct} removes duplicates. Evaluation proceeds left to right by nested iteration over the variables' domains, binding each variable when it is first needed and abandoning a binding as soon as a conjunct fails.

\emph{Positive} queries, which select variables and whose condition uses only class and property atoms, equality, conjunction, disjunction and existential quantification, are monotone: adding facts to $\mathcal{A}$ never removes an answer. The remaining constructs, including aggregates, are deliberately closed-world. A query for students who take at most one course counts the courses in $\mathcal{A}$, whereas an OWL reasoner cannot conclude that a student takes at most one course without knowing all of them.

\subsection{Complexity}
\label{ssec:eql_complexity}

The complexity of \ac{eql} follows from known results, which the supplementary material tabulates; we state it for deciding whether a tuple is an answer. \emph{Data complexity} fixes the query and measures cost in the size of $\mathcal{A}$, which is what matters for a deployed agent. \emph{Combined complexity} lets the query vary as well. Unions of conjunctive queries are in AC$^0$ in data and NP-complete in combined complexity~\cite{ChandraMerlin1977,AbiteboulHullVianu1995}. With negation and universal quantification, \ac{eql} conditions express first-order logic under the active-domain semantics, which is PSPACE-complete in combined complexity~\cite{Vardi1982} and in AC$^0$ in data complexity~\cite{immerman1987languages,barrington1990uniformity}. Aggregates over numbers of polynomial length raise data complexity to TC$^0$~\cite{hella2001aggregate,libkin2003expressive}. Predicates and symbolic functions are arbitrary Python code, so we treat them as oracles. A query $\varphi$ with $k$ variables, including quantified ones, over domains of size at most $d$ calls them at most $|\varphi|\cdot d^{k}$ times. For a fixed query, $k$ is a constant, so this bound is polynomial in $d$; in combined complexity it is exponential. Evaluation therefore runs in time polynomial in the size of $\mathcal{A}$ whenever the domains have polynomial size and the callables run in polynomial time. Termination of arbitrary callables cannot be guaranteed. The bounds concern queries; rules (Section~\ref{ssec:eql_syntax}) are evaluated as single queries.


\section{Ontomatic: Compiling OWL 2 RL Ontologies}
\label{sec:ontomatic}

Ontomatic turns an OWL ontology into a \ac{krrood} knowledge base in two phases. TBox compilation generates Python modules with classes, property descriptors and axioms. ABox loading creates the objects and materializes the consequences of the ontology. Ontomatic targets the OWL~2~RL profile~\cite{motik2012owl2profiles}, which was designed for rule-based implementations. Entailment of assertions in OWL~2~RL is captured by a fixed set of first-order rules over RDF triples, the OWL~2~RL/RDF rules~\cite[Section~4.3]{motik2012owl2profiles}. The specification names each rule by what it reasons about (\texttt{eq} equality, \texttt{prp} properties, \texttt{cls} class expressions, \texttt{cax} class axioms, \texttt{dt} datatypes, \texttt{scm} the schema) and by the construct it handles. For example, \texttt{prp-dom} derives $C(x)$ from $P(x,y)$ if $P$ has domain $C$. For an RL ontology without punning and without annotation-property axioms, an assertion $C(a)$, $P(a,b)$ or $\mathit{SameIndividual}(a,b)$ is entailed if and only if it follows from the RL/RDF rules applied to the ontology's RDF translation~\cite[Theorem PR1]{motik2012owl2profiles}. Ontomatic realizes the rules with the mechanisms of Section~\ref{sec:kr}. Table~\ref{tab:rl} lists the correspondence, including the rules that \ac{krrood} does not apply but checks after loading.

\paragraph{TBox compilation}
Named classes become Python classes related by inheritance. Every object property becomes a descriptor class, whose bases encode its super-properties and characteristics, and an attribute of its domain class, typed by its range. Domains and ranges that are not declared are derived from equivalent, inverse and super-properties, falling back to the ontology's root class. These schema-level rules were built incrementally as a ripple-down rule base~\cite{compton2021rdr}. Class expressions that state sufficient conditions for membership become axioms. These are \texttt{hasValue} definitions (Listing~\ref{lst:axiom}) and class expressions in subclass position, such as $\texttt{Person}\sqcap\exists\texttt{loves}.\texttt{Sports}\sqsubseteq\texttt{SportsLover}$. Restrictions in superclass position state necessary conditions, which never make an individual a member of the class: they refine the types of attributes, and loading applies them to the members of the class (Table~\ref{tab:rl}). Classes whose instances may also belong to unrelated classes are generated as roles. The ontology marks them with a restriction on an auxiliary property \texttt{roleFor}, which we added to OWL2Bench for the classes that represent roles of a person or an organization.

\paragraph{ABox loading and materialization}
Ontomatic (Algorithm~\ref{alg:loading}) never changes the class of an object it has created, so it infers all types before any object exists. Steps~1 and~2 work on lightweight proxies of the individuals; step~2 also applies transitivity and chains to the properties that class expressions and chains use, and evaluates the axioms in a compiled Python form for speed. Step~3 creates the objects and their roles. Step~4 assigns each property value, asserted or required by a \texttt{hasValue} restriction, through its descriptor, on an object of the subject whose class declares the property and to an object of the value that fits its range. Each assignment triggers the assign rules of Table~\ref{tab:rl}, for asserted and inferred facts alike, until no new fact arises. Transitive properties that are also symmetric are an exception. Chaining them on every assignment is expensive (Section~\ref{sec:experiments}), so step~5 completes them at once: within each weakly connected component of such a property's graph, every pair of individuals is related. This is exact, because the transitive and symmetric closure of a graph relates exactly the members of each connected component. If the property has a super-property, an inverse, an equivalent property or occurs in a property chain, the facts added in this step are then propagated like any other fact. Otherwise they are stored directly, and their provenance is the component.

\begin{algorithm}[t]
\caption{ABox loading in Ontomatic (\texttt{OwlLoader.load}).}
\label{alg:loading}
\small
\begin{algorithmic}[1]
\Require RDF graph $G$ of the ABox, generated model
\State \textbf{for each} individual $i$ of $G$: $p_i \gets$ a proxy with the asserted types and values of $i$ and those implied by sub-, inverse and symmetric properties \Comment{Step 1}
\Repeat \Comment{Step 2}
  \State apply chains and transitivity where types depend on them
  \For{each proxy $p_i$}
    \State add the domains and ranges of the properties of $p_i$
    \State add the classes whose axioms $p_i$ satisfies
    \State add what the necessary conditions of its classes require
  \EndFor
\Until{no type or value is added}
\State \textbf{for each} proxy $p_i$: $O_i \gets$ one object per most specific type \Comment{Step 3}
\For{each $P(i,j)$ asserted or required by \texttt{hasValue}} \Comment{Step 4}
  \State add the object of $O_j$ fitting $P$'s range to $P$ on the object of $O_i$ declaring $P$; the rules of $P$ fire
\EndFor
\State \textbf{for each} weakly connected component $C$ of a symmetric, transitive $P$: add $P(a,b)$ for all $a, b \in C$ \Comment{Step 5}
\State \Return the objects $O_i$
\end{algorithmic}
\end{algorithm}

\paragraph{What is preserved}
The loading procedure is sound with respect to OWL~2~RL:

\begin{proposition}[Soundness]
\label{prop:soundness}
Let $\mathcal{O}$ be an OWL~2~RL ontology without punning, and let $\mathcal{A}^*$ be the knowledge base that Ontomatic produces from it. Every class and property assertion of $\mathcal{I}_{\mathcal{A}^*}$ is entailed by $\mathcal{O}$. Consequently, every answer of a positive \acs{eql} query over $\mathcal{A}^*$ is a certain answer over $\mathcal{O}$.
\end{proposition}

The first statement holds because every fact that Algorithm~\ref{alg:loading} derives is the conclusion of an RL/RDF rule of Table~\ref{tab:rl}, or of a sequence of them. This includes the schema-level derivation of domains and ranges, which only composes \texttt{prp-dom}, \texttt{prp-rng}, \texttt{prp-inv} and \texttt{prp-eqp}. The second statement holds because positive queries are preserved under homomorphisms, and $\mathcal{I}_{\mathcal{A}^*}$ maps homomorphically into every model of $\mathcal{O}$, including models that identify individuals that \ac{krrood} keeps apart. For an inconsistent $\mathcal{O}$ the guarantee is vacuous; the check described next reports the inconsistencies that the rules of Table~\ref{tab:rl} derive from $\mathcal{A}^*$.

\ac{krrood} does not merge individuals. Instead, a check after loading evaluates on $\mathcal{A}^*$ the RL/RDF rules that derive the equality of two individuals (\texttt{prp-fp}, \texttt{prp-ifp}, \texttt{prp-key}, \texttt{cls-maxc2}, \texttt{cls-maxqc3/4}) or an inconsistency (Table~\ref{tab:rl}), and reports every application. If none applies and $\mathcal{O}$ uses only the constructs of Table~\ref{tab:rl}, the unique-name assumption is entailed rather than assumed, and the converse of Proposition~\ref{prop:soundness} holds:

\begin{proposition}[Completeness]
\label{prop:completeness}
Let $\mathcal{O}$ and $\mathcal{A}^*$ be as in Proposition~\ref{prop:soundness}, let $\mathcal{O}$ use only the constructs of Table~\ref{tab:rl}, and let the check report no equality and no inconsistency. Then every class assertion $C(a)$, with $C$ a named class, and every object- and data-property assertion entailed by $\mathcal{O}$ holds in $\mathcal{I}_{\mathcal{A}^*}$.
\end{proposition}

By Theorem PR1 of the OWL~2 profiles specification~\cite{motik2012owl2profiles}, such an assertion follows from the RL/RDF rules, so it suffices that $\mathcal{A}^*$ with the reflexive \texttt{sameAs} facts is closed under them. By the check, no equality or inconsistency rule applies. The property rules are applied to every fact, and the typing rules to every fact known in step~2, which closes the properties that class expressions and chains use. A fact derived later by transitivity relates two individuals that already have facts of the property, so it adds no domain or range. Every fact is stored on an object that declares the property, which exists because step~2 typed the subject with the property's domain.

\section{ORMatic: Long-Term Memory}
\label{sec:ormatic}

An agent also needs to keep knowledge beyond the lifetime of its process, for example as an episodic memory of what it has done~\cite{beetz2025robot}, and often more of it than fits in working memory. ORMatic is \ac{krrood}'s persistence layer and serves as the agent's long-term memory. From the same classes that form the TBox, it generates a relational schema and data access objects (DAOs) for SQLAlchemy, together with routines that convert objects to DAOs and back. The domain model therefore remains the single definition of the agent's knowledge: ORMatic automates keeping the schema in sync with it, the domain classes remain free of persistence code, and generated mappings can be customized. The database adds what working memory lacks for large amounts of data: indexes, a query optimizer that chooses how to evaluate each query~\cite{selinger1979access}, and tables that learning components can read directly.

\begin{lstlisting}[style=eql, float=t, caption={One \acs{eql} query evaluated in working memory and, translated by ORMatic, in long-term memory.}, label={lst:ormatic}]
s = variable(Student, domain=students)
over_25 = an(entity(s).where(s.has_age > 25))  # via role taker
in_memory = list(over_25.evaluate())              # working memory
stored = eql_to_sql(over_25, session).evaluate()  # long-term memory
\end{lstlisting}

Because an \ac{eql} query is a symbolic expression that is separate from its evaluation, the same query can be evaluated in working memory or translated to SQL and evaluated in the database (Listing~\ref{lst:ormatic}). The translator maps a variable to the table of its class and an attribute chain to joins, here of \texttt{Student} with \texttt{Person} on the role taker. Every object property that Ontomatic generates is collection-valued, and such an attribute is stored as rows of an association table: ranging over its elements becomes a join, and membership and existential quantification become correlated \texttt{EXISTS} subqueries. Universal quantification, predicates and functions, which run Python code, and rules, which create objects, are not translated; the translator rejects them instead of answering differently. On a test database over the part of the OWL2Bench model that the benchmark queries use, the translations of all 18 queries return the same answers as \ac{eql}. The SQL queries of our experiments (Section~\ref{sec:experiments}) were not produced by the translator: they were written with SQLAlchemy with the help of an AI assistant and verified by the authors against GraphDB's answers.

\paragraph{Setup}
We use the OWL~2~RL profile of OWL2Bench~\cite{singh2020owl2bench} with one university: 3,667 individuals and 54,901 explicit statements; its closure, computed by GraphDB, has 1,431,635 statements and is the pre-reasoned input. We run all 18 queries of the RL profile (Q2--5, Q7--16, Q19--22). Ontomatic generates the \ac{krrood} model from the ontology with our \texttt{roleFor} markers (Section~\ref{sec:ontomatic}). For the SQL queries, ORMatic persists the loaded objects in PostgreSQL.

We compare against four systems: GraphDB 11.2 with the OWL~2~RL ruleset, in the free edition, which is limited to one CPU core; RDFLib 7.4 with the \texttt{owlrl} OWL~2~RL reasoner; Owlready2 0.49 with its bundled Pellet; and Protégé 5.6.7 with Pellet.
GraphDB and \texttt{owlrl} materialize the OWL~2~RL rules and are therefore the like-for-like baselines. We use GraphDB's answers as the reference, because its ruleset implements the rules that define OWL~2~RL entailment. Pellet is claimed complete for OWL~DL~\cite{sirin2007pellet}, but we know of no verification of its answers on OWL2Bench~\cite{singh2020owl2bench}. All systems load the same ontology file, including the \texttt{roleFor} markers. All experiments ran on Ubuntu 24.04 with an Intel Core i7-13700 and 64\,GB of RAM, all but Protégé in Docker containers.\footnote{The supplementary material contains the code, the data and the Docker set-up, which runs every experiment except Protégé's, including the answer comparison.} Query times are means over 10 consecutive runs in one process, including the first. Loading runs of GraphDB, RDFLib, Protégé and the ablation are single runs; RDFLib is stopped after three hours and the ablation after two. Memory is the increase of the peak resident set size of the process tree, or of the Java heap in use for GraphDB (8\,GB heap, separate load) and Protégé (28\,GB heap).

\subsection{Correctness}
\label{ssec:correctness}

We normalized each system's answers to sets of tuples of IRIs and literals and compared them with GraphDB's. RDFLib, Owlready2, \ac{eql} and SQL over ORMatic return answer sets identical to GraphDB's on all 18 queries. Protégé, without a programmatic query interface, returns GraphDB's numbers of answers on the 16 queries it completes. Q9, Q13 and Q14 have empty answers in every system, because the RL ontology entails no instances for them. We also compared the knowledge base produced by Ontomatic with GraphDB's OWL~2~RL closure, assertion by assertion. For all 3,667 individuals, the 17,558 class memberships coincide, with none missing or extra, and so do the 1,385,869 object-property and the 20,933 data-property assertions. OWL2Bench declares functional and inverse-functional properties, such as those of Q4, Q15 and Q16, yet the check of Section~\ref{sec:ontomatic} finds no equality and no inconsistency, so on this knowledge base the unique-name assumption is entailed. This confirms Propositions~\ref{prop:soundness} and~\ref{prop:completeness} on the benchmark, to which they do not apply directly: OWL2Bench uses 47 IRIs both as classes and as individuals, and our \texttt{roleFor} markers lie outside OWL~2~RL, although they change no entailment, as every marked class is already a subclass of the marker's filler.

Q12 shows how roles reconcile OWL entailment with object types. In OWL2Bench, \texttt{hasResearchProject} is a sub-property of \texttt{hasWork}, whose domain is \texttt{Employee}, so every research group with a research project, as all in the data have, is entailed to be an employee, and thus a person. A \texttt{ResearchGroup} object cannot become a \texttt{Person} by inheritance, so \ac{krrood} gives the research group's individual a second object, a \texttt{Person} with an \texttt{Employee} role. Q12 then returns GraphDB's 2,494 persons, and application code keeps a well-typed \texttt{ResearchGroup} object; the two objects carry the same IRI and denote one individual, but neither refers to the other. As \ac{eql} reads an attribute on a variable's object or its role taker, and Ontomatic stores each fact on the subject's object that declares the property, \ac{eql}'s answers, mapped by $\mathit{ind}$ and without duplicates, are those of Section~\ref{ssec:eql_semantics} if every individual is denoted by one object and its roles and every attribute is read on a variable whose class declares it; in OWL2Bench, all individuals but these 7 research groups are.

\subsection{Loading and Reasoning}

From raw data (Table~\ref{tab:baselines}), \ac{krrood} computes the closure in 8.2\,s, and GraphDB, disk-based and on its single core, in 1,210\,s. From pre-reasoned data, \ac{krrood} takes 89.2\,s and GraphDB 748\,s. \ac{krrood}'s memory grows with the data, from 209\,MB to 1.81\,GB, as it holds every fact as an object; GraphDB's heap grows by at most 860\,MB, its data being on disk. Pellet in Owlready2 exceeds its default 2\,GB Java heap on pre-reasoned data. Persisting with ORMatic adds 20--25\,s. Without step~5, loading takes over two hours: on synthetic data, eager chaining derives the same facts with work cubic in the number of individuals sharing a home town, 1,145 in OWL2Bench. Protégé is the fastest, as Pellet derives facts when queried: its first query took up to 46\,s, and Q20 did not finish in 60\,s.

\subsection{Querying}

In Table~\ref{tab:queries}, SQLAlchemy queries the data that ORMatic persisted; its times include building rows or DAOs, not converting them into domain objects. Only \ac{eql} returns objects of application code.

SQLAlchemy has the lowest geometric mean and is the fastest on 13 of the 18 queries; \ac{eql}'s is 1.7 times GraphDB's, below RDFLib's and Owlready2's. \ac{eql} is faster than GraphDB on 8 queries, all with at most 858 answers, three times slower on Q20, with 1.3 million answers, and slowest on Q22, the join of Listing~\ref{lst:q22}: 214\,ms against 1.4\,ms. SQL over the objects that ORMatic persisted answers Q22 in 9.4\,ms, so the gap lies in how \ac{eql} evaluates joins, not in the object model.

\section{Discussion and Conclusion}
\label{sec:discussion_conclusion}

We presented \ac{krrood}, which turns an agent's object-oriented program into its knowledge base, read and written by attribute access and reasoned over with the agent's own procedures. On OWL2Bench, it returns the same answers as an OWL~2~RL reasoner, its knowledge base equals the reasoner's closure, and its loading and query times lie within the range of established systems, its query times being 1.7 times GraphDB's in geometric mean.

\paragraph{Limitations and future work}
\ac{krrood} adopts the closed-world and unique-name assumptions: it reports equal individuals without merging them, and where Proposition~\ref{prop:completeness} does not apply, a closed-world answer can contradict OWL entailment. Partial, noisy observation challenges this reading. Ontomatic does not yet compile some RL constructs, such as \texttt{oneOf}. Inferred facts are not retracted; changing state, such as a robot's pose, can instead be computed by predicates. We evaluated a single benchmark scale. We will maintain inferred facts incrementally~\cite{MotikNenovPiroHorrocks2015}, extend Ontomatic towards OWL~DL, plan \ac{eql}'s joins, and evaluate \ac{krrood} on real robots.
