\begin{abstract}
Robots and other autonomous agents are often built on cognitive architectures, whose modules for perception, planning, control, learning and memory share knowledge. We consider architectures whose modules are object-oriented programs. When such an agent represents its knowledge in OWL or RDF to perform logical inference, the knowledge lives in a second representation, with assumptions of its own, that must be kept synchronized with the program. We present KRROOD, a framework that unifies the two: the agent's object-oriented program is its knowledge base. Classes and property descriptors form the terminology, live objects form the assertions, and property rules fire when facts are asserted. The Entity Query Language (EQL) queries the program with a formal, closed-world semantics, and its predicates and functions are the agent's own procedures, so reasoning combines logical inference with computation on the agent's data. Ontomatic compiles OWL~2~RL ontologies into such programs, with guarantees of soundness and, under conditions we identify, completeness for positive queries. ORMatic stores the same objects in a relational database as long-term memory, which EQL queries through a translation to SQL. On the OWL2Bench benchmark, KRROOD's knowledge base equals an OWL~2~RL reasoner's closure, assertion by assertion, and its queries return the same answers. Its loading costs, and its query costs in geometric mean, are within the range of established OWL and RDF systems. In a perceive--decide--act loop, a delivery robot built on KRROOD makes the same decisions as robots built on GraphDB, Nemo and Owlready2, without code that keeps two representations in sync.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Robots and other autonomous agents are often built on cognitive architectures that organize perception, planning, control and learning into modules sharing knowledge about the world and the task~\cite{langley2009cognitive,kotseruba2020cognitive}. In robotics, this knowledge is often made explicit, shareable and open to sound inference in ontologies, commonly written in the Web Ontology Language (OWL)~\cite{olivares2019review,Tenorth2013,delgrande2024current}. We consider architectures whose modules are object-oriented programs, in which perception produces objects and planners and controllers manipulate them~\cite{beetz2025robot}. For a developer, the practical value of such an ontology depends on how well it integrates with the agent's \emph{application code}, the program that perceives, decides and acts~\cite{ledvinka2020comparison}.

When the knowledge lives outside the program, for example in a reasoner or a triple store, integration means keeping two \emph{world models}: the program's objects and the ontology's individuals, each with its own concerns~\cite{davis1993knowledge}. OWL is designed for sound inference over possibly incomplete knowledge and assumes an open world, in which a missing fact is unknown, whereas programs and databases are designed for computing over data that they treat as complete~\cite{Reiter1978}; the two also treat names and inconsistencies differently~\cite{motik2009bridging}. In practice, the program's state is translated, a reasoner is invoked on the exported copy and the results are mapped back, with these differences handled at each step. This is an object-ontological counterpart of the object-relational impedance mismatch~\cite{ireland2015exposing,ledvinka2020comparison}.

A second requirement comes from the agent itself. Reasoning in robotics goes beyond logical inference over stated facts. Much of what a robot knows is computed from its own data. For example, whether an object is on a table follows from the poses that perception estimates~\cite{beetz2018know}. KnowRob~\cite{Tenorth2013,beetz2018know} therefore attaches procedures, called computables, to the predicates of its knowledge base. A knowledge representation for such agents has to let reasoning call the agent's own code.

This paper argues that this knowledge can instead be \emph{represented explicitly in the agent's object-oriented program}, so that the program itself becomes the knowledge base and its procedures take part in reasoning. We present \acf{krrood}, a Python framework built on this idea (Figure~\ref{fig:arch}). Classes and property descriptors form the TBox and live objects the ABox, and property rules fire when application code asserts a fact. A query language with a formal, closed-world semantics reasons over the objects directly, and its predicates and functions are ordinary Python callables, so reasoning in \ac{krrood} is not limited to logical inference. We use Python, common in robotics, whose operator overloading allows a query language to be embedded in it. We make four contributions:

\begin{enumerate}
\item An object-oriented knowledge representation with a formal reading as a knowledge base, in which properties are first-class descriptors that carry their logical characteristics, multiple classification is handled by roles, and predicates are computed by the agent's own code (Section~\ref{sec:kr}).
\item The \acf{eql}, a query language embedded in Python, with a formal, closed-world semantics, in which class axioms and rules are ordinary query conditions and the agent's procedures are predicates (Section~\ref{sec:eql}).
\item Ontomatic, which compiles OWL~2~RL ontologies into such programs (Section~\ref{sec:ontomatic}). Positive queries over the compiled program are sound, and complete under conditions we identify. Its property rules stay valid as the agent asserts new facts.
\item ORMatic, which generates from the same classes a relational schema that serves as the agent's long-term memory, and translates a subset of \ac{eql} to SQL (Section~\ref{sec:ormatic}).
\end{enumerate}
At runtime, the guarantees concern added facts and property assertions: class memberships are not derived, and inferred facts are not retracted (Section~\ref{sec:discussion_conclusion}).

Our evaluation asks whether this unification is faithful and comes at an acceptable cost (Section~\ref{sec:experiments}).\footnote{Source code, experiment scripts and the full formalization of \ac{eql} are in the anonymized supplementary material.} We evaluate on the OWL2Bench benchmark~\cite{singh2020owl2bench}. We compare \ac{krrood}'s knowledge base and answers with those of OWL~2~RL reasoners, after loading and while an agent asserts facts. We measure loading, persisting and querying costs against established OWL and RDF systems, and we run a delivery robot built with \ac{krrood}, GraphDB, Nemo and Owlready2.

\section{Related Work}
\label{sec:related-work}

\paragraph{Objects mapped to ontologies}
Object-ontology mappers generate or annotate classes whose instances stand for individuals, while the ontology store or an external reasoner remains authoritative: Jastor~\cite{szekely2009jastor}, the mapping of Kalyanpur et al.~\cite{kalyanpur2004automatic}, KOMMA~\cite{wenzel2010komma} and JOPA~\cite{ledvinka2016jopa} in Java, and Owlready2~\cite{lamy2017owlready} in Python. Owlready2's objects are proxies of the individuals in a quadstore; it runs Pellet or HermiT in batch on the store and writes the inferred facts back. The OWL API~\cite{horridge2011owl}, OWLAPY~\cite{baci2025owlapy} and OWLOOP~\cite{buoncompagni2024owloop} model axioms, LITEQ~\cite{leinberger2014liteq} and $\lambda_{DL}$~\cite{leinberger2017essence} give types to queries over a store's RDF data, and ontology-based data access~\cite{poggi2008linking,calvanese2017ontop,calvanese2011mastro} maps ontology queries to a relational database. In \ac{krrood}, by contrast, the program's classes are the terminology, descriptors apply property semantics when a value is assigned, the closure lives in the program's objects, and ORMatic derives the schema from the classes.

\paragraph{Reasoners and materialization}
OWL reasoners such as Pellet~\cite{sirin2007pellet}, HermiT~\cite{glimm2014hermit} and RacerPro~\cite{haarslev2012racerpro} decide entailment for expressive description logics, and rule engines such as RDFox~\cite{nenov2015rdfox}, VLog~\cite{carral2019vlog}, GraphDB, Soufflé~\cite{jordan2016souffle} and Nemo~\cite{ivliev2024nemo} materialize rules, OWL~2~RL among them~\cite{grosof2003description}, in their own stores. \ac{krrood} materializes them in application objects and interprets queries under the closed-world semantics that Motik et al.~\cite{motik2009bridging} and Tao et al.~\cite{tao2010integrity} give to OWL integrity constraints.

\paragraph{Queries and rules in the host language}
LINQ~\cite{meijer2006linq} and Pony ORM~\cite{ponyorm} embed queries in a programming language; pyDatalog~\cite{carbonnelle2020pydatalog}, ProbLog~\cite{dries2015problog2} and ErgoAI with F-logic~\cite{kifer2018ergoai,kifer1995flogic} embed logic programs, and production rule systems (CLIPS/COOL~\cite{giarratano2005expert}, Jess~\cite{friedmanhill2003jess}, Drools~\cite{proctor2012drools}) match rules in their own language, without ontological semantics, against objects inserted into a Rete engine~\cite{forgy1982rete}. Deductive object bases such as ConceptBase~\cite{jarke1995conceptbase} combine objects and rules under a formal semantics in a store of their own. KnowRob~\cite{Tenorth2013,beetz2018know} reasons in Prolog over an OWL triple store in a separate process that the program updates. All of these keep the terminology outside the application's classes; predicate classes~\cite{chambers1993predicate} come closest, classifying an application's objects by a condition, as \ac{krrood}'s axioms do. \ac{eql} adds first-order queries and rules over the program's own objects, whose concepts, properties and predicates are classes.

\paragraph{Ontologies in agent programming}
JADE maps messages to classes of an ontology's schemas~\cite{bellifemine2007jade,caire2010jadeontology}. AgentSpeak-DL~\cite{moreira2006agentspeakdl} and JASDL~\cite{klapiscak2009jasdl} add description-logic reasoning to BDI belief bases, which on most agent platforms still lack ontological inference and queries~\cite{burattini2025gap,longo2025t2b2t}. JaCaMo maps Java artifacts to beliefs~\cite{boissier2013jacamo,ricci2011cartago}, and Soar's working memory is a graph of its own elements~\cite{laird2012soar}. In \ac{krrood}, the counterpart of a belief base is the program's objects, with OWL~2~RL inference and queries over them.

\section{Knowledge Representation in KRROOD}
\label{sec:kr}

In \ac{krrood}, the knowledge base of an agent is its object-oriented program. We use one running example throughout the paper: an assistant agent for a university whose knowledge comes from the OWL2Bench university ontology~\cite{singh2020owl2bench}. Its \emph{application code}, which for instance suggests courses to students, manipulates \texttt{Person}, \texttt{Student} and \texttt{Course} objects, which are also the individuals of its knowledge base.

\paragraph{Vocabulary}
A \ac{krrood} knowledge base is a pair $\mathcal{K}=(\mathcal{T},\mathcal{A})$. The TBox $\mathcal{T}$ consists of Python declarations of four kinds:
\begin{itemize}
  \item \emph{Concepts} are classes. Subsumption between named concepts is declared by inheritance, and \texttt{issubclass} computes its reflexive-transitive closure.
  \item \emph{Properties} (binary relations) are attributes. Each attribute is managed by a \emph{property descriptor}, a class whose position in the descriptor hierarchy encodes property subsumption (in OWL2Bench's vocabulary, \texttt{IsCrazyAbout} $\sqsubseteq$ \texttt{Loves} $\sqsubseteq$ \texttt{Likes}). Its \emph{mixins}~\cite{bracha1990mixin}, base classes that each add one behavior, encode property characteristics such as transitivity, symmetry, inverses and property chains.
  \item \emph{Axioms} that typing and inheritance cannot express, such as the definition of a class by a necessary and sufficient condition (\texttt{T20CricketFan} in Listing~\ref{lst:axiom}), are class methods that return an \ac{eql} condition (Section~\ref{sec:eql}) characterizing the members of the class. Because $\mathcal{K}$, like a relational database~\cite{reiter1984relational}, has a single interpretation, an axiom does not constrain models as in a description logic~\cite{baader2003dlhandbook}. It is a condition that can be checked, like an integrity constraint~\cite{motik2009bridging,tao2010integrity}, or used to classify individuals (Section~\ref{sec:ontomatic}).
  \item \emph{Predicates and symbolic functions} are Python callables that can appear as atoms of \ac{eql} conditions. They give reasoning direct access to the agent's own procedures, such as the reachability check of Listing~\ref{lst:agent}.
\end{itemize}
The ABox $\mathcal{A}$ consists of the live objects and their attribute values, which form the agent's \emph{working memory}. Listing~\ref{lst:kr} shows part of the running example. Its last statement attaches a descriptor to a class attribute: from then on, every read and write of \texttt{is\_crazy\_about} on a \texttt{Person} passes through \texttt{IsCrazyAbout}, which applies the property's rules.\footnote{Listings are simplified. They use the current version of \acs{krrood}; Ontomatic (Algorithm~\ref{alg:loading}) and the experiments use an earlier version, and the supplement contains both.}

\begin{lstlisting}[style=eql, caption={Part of the running example. Classes are concepts, attributes are properties, and descriptor classes carry property semantics.}, label={lst:kr}]
@dataclass(eq=False)
class Person(Thing):
    is_crazy_about: set[Interest]
@dataclass(eq=False)
class Student(Role[Person]):  # played by a Person
    takes_course: set[Course]
class Likes(PropertyDescriptor): ...
class Loves(Likes): ...
class IsCrazyAbout(Loves): ...  # sub-property
class IsPartOf(PropertyDescriptor, TransitiveProperty): ...
# IsCrazyAbout manages Person.is_crazy_about
Person.is_crazy_about = IsCrazyAbout(Person,
                                     "is_crazy_about")
\end{lstlisting}

\paragraph{Multiple classification through roles}
An OWL individual may belong to classes unrelated by subsumption, such as \texttt{Student} and \texttt{SportsFan}, but a Python object has a single most specific class, and multiple inheritance would need a class for every combination, fixed when the object is created. \ac{krrood} resolves this with the Role pattern~\cite{steimann2000roles,Guarino2004,boella2007roles}, whose implementations in Python have been compared~\cite{bassiouny2026roles}. In this paper ``role'' refers only to this pattern: a role is an object of its own class that refers to the entity playing it, its \emph{role taker}, and delegates to it reads of every attribute it does not declare itself (\texttt{Student} in Listing~\ref{lst:kr}). A student who is also a sports fan is one \texttt{Person} object with a \texttt{Student} role and a \texttt{SportsFan} role, so the individual keeps a single identity.

\paragraph{Interpretation}
$\mathcal{K}$ has a single interpretation $\mathcal{I}_{\mathcal{A}}$, which assigns a set of individuals to every concept and a set of pairs to every property. Objects and individuals do not correspond one to one. We write $\mathit{ind}(o)$ for the individual that object $o$ denotes. A role denotes the individual of its role taker, an object created for an ontology individual denotes the individual of its IRI, and any other object denotes an individual of its own. On data values, such as numbers and strings, $\mathit{ind}$ is the identity. With $O$ the set of objects in memory, a concept $C$ denotes $C^{\mathcal{I}}=\{\mathit{ind}(o)\mid o\in O \text{ is an instance of } C\}$. A property $P$ that manages attribute $p$ relates the individual of every object to the individual of every value of its attribute: $P^{\mathcal{I}}=\{(\mathit{ind}(o),\mathit{ind}(v))\mid o\in O,\ v \text{ is } o.p \text{ or an element of } o.p\}$. A predicate denotes the tuples for which its code returns true, and a symbolic function the function its code computes. Their extensions are not stored in $\mathcal{A}$ but computed when a query needs them, like the computables of KnowRob~\cite{Tenorth2013}. $\mathcal{K}$ is read under the assumptions of relational databases~\cite{Reiter1978,reiter1984relational}. \emph{Closed world:} a ground atom, such as $\texttt{Student}(\mathit{alice})$ or a predicate applied to values, is false unless $\mathcal{I}_{\mathcal{A}}$ makes it true, which for a predicate means that its code returns true. \emph{Domain closure:} there are no individuals other than those that objects denote. \emph{Unique names:} two objects denote the same individual only if they carry the same IRI or one is a role of the other, directly or through further roles. These are the assumptions under which application code typically treats its objects; Section~\ref{sec:ontomatic} reconciles them with OWL.

\paragraph{Reasoning inside the program}
Property descriptors apply the consequences of a fact when application code asserts it: assigning a value to an attribute triggers forward chaining over the descriptor's characteristics. For example, adding T20 cricket to \texttt{p.is\_crazy\_about} also adds it to \texttt{p.loves} and \texttt{p.likes}. Class membership is derived when knowledge is loaded (Section~\ref{sec:ontomatic}) or by rules on request (Section~\ref{sec:eql}). Inferred property facts are marked as inferred. $\mathcal{K}$ is queried, and axioms are evaluated, with \ac{eql}.

\section{EQL: Querying the Program as a Knowledge Base}
\label{sec:eql}

\ac{eql} is a declarative query language embedded in Python. An \ac{eql} query is a Python expression built from symbolic variables, whose names and types the development environment can check, and it is evaluated in the program's own language and process, directly over its live objects. This continues the idea of language-integrated queries~\cite{meijer2006linq}, adding first-order formulas, negation as failure, quantifiers, rules and user-defined predicates. The supplementary material contains the full formalization of its syntax, semantics and complexity.

\subsection{Syntax}
\label{ssec:eql_syntax}

\paragraph{Variables and terms}
A variable \texttt{x = variable(C, domain=D)} is a symbol ranging over the instances of class $C$ in a finite collection $D$. If $D$ is omitted, it is the set of all known instances of $C$. Because $D$ can be any collection computed by the program, a query can be restricted to the task-relevant part of the knowledge base. Terms are built from constants, variables, attribute access \texttt{t.a}, indexing \texttt{t.a[i]}, method calls \texttt{t.m($\bar t$)} and symbolic functions \texttt{f($\bar t$)}. Chains of attribute accesses replace most joins of relational query languages.

\paragraph{Atoms and formulas}
An atom is a predicate applied to terms, $p(\bar t)$, a comparison $t_1 \mathbin{\mathsf{op}} t_2$ with $\mathsf{op}\in\{=,\neq,<,\le,>,\ge,\in\}$, or a Boolean-valued term. Formulas are built by
\[
\varphi ::= \alpha \mid \varphi\wedge\varphi \mid \varphi\vee\varphi \mid \neg\varphi \mid \exists x\in D.\,\varphi \mid \forall x\in D.\,\varphi ,
\]
written as several arguments of \texttt{where}, \texttt{or\_}, \texttt{not\_}, \texttt{exists} and \texttt{for\_all}. A domain may depend on outer variables: \texttt{flat\_variable(s.takes\_course)} ranges over the courses of each student $s$.

\paragraph{Queries}
A query selects one or more variables, \texttt{entity(x)} or \texttt{set\_of(x, y)}, constrained by \texttt{.where($\varphi$)}, and is wrapped in a result quantifier. The result quantifier \texttt{an} accepts any number of answers; \texttt{the} requires exactly one, as in Russell's definite description~\cite{russell1905denoting}, and raises an error otherwise. Aggregates with \texttt{grouped\_by} and \texttt{having} follow relational grouping~\cite{Klug1982}.

Listing~\ref{lst:q22} shows OWL2Bench query Q22, ``students who take a course taught by the dean of an organization'', in SPARQL and in \ac{eql}. Each triple pattern becomes an attribute chain or a membership atom: no join keys are written, and the only join is the membership atom.

\begin{lstlisting}[style=eql, caption={OWL2Bench query Q22 in SPARQL (top) and \acs{eql} (bottom).}, label={lst:q22}]
SELECT ?s ?c WHERE { ?s a :Student .
  ?o a :Organization . ?o :hasDean ?d .
  ?d :teachesCourse ?c . ?s :takesCourse ?c }
\end{lstlisting}
\vspace{-0.9\baselineskip}
\begin{lstlisting}[style=eql]
s = variable(Student, domain=students)
o = variable(Organization)
dean = flat_variable(o.has_dean)
c = flat_variable(dean.teaches_course)
q22 = an(set_of(s, c).where(contains(s.takes_course, c)))
\end{lstlisting}

\paragraph{Axioms and rules}
Since an axiom is a class method returning an \ac{eql} condition, it can be inspected, used as a constraint, or used as the body of a rule. Listing~\ref{lst:axiom} shows the OWL2Bench definition $\texttt{T20CricketFan}\equiv\exists\texttt{isCrazyAbout}.\{\texttt{T20Cricket}\}$ as an axiom, and a rule that derives a \texttt{T20CricketFan} role for every person satisfying it. In general, a rule \texttt{inference(H)($\bar k$)} derives an instance of class $H$ for each answer of its body. Like an object identifier created by a Skolem functor~\cite{hull1990ilog}, a derived object is identified by its class and its arguments. Evaluating the rule again, or another rule with the same class and arguments, returns the same object, so rule evaluation is idempotent. A rule is evaluated on request, like a query, and returns the derived objects. Rules are not recursive: the body of a rule is a single query, and recursion, such as transitivity, comes only from property descriptors.

\begin{lstlisting}[style=eql, caption={An OWL class definition as an axiom, used as the body of a classification rule.}, label={lst:axiom}]
@dataclass(eq=False)
class T20CricketFan(SportsFan):
    @classmethod
    def axiom(cls, p):
        return contains(p.is_crazy_about, T20_CRICKET)

p = variable(Person)
fan = inference(T20CricketFan)(role_taker=p)
fans = an(entity(fan).where(T20CricketFan.axiom(p)))
\end{lstlisting}

\subsection{Semantics}
\label{ssec:eql_semantics}

A query $Q(\bar x)\leftarrow\varphi(\bar x,\bar y)$ is evaluated in the single interpretation $\mathcal{I}_{\mathcal{A}}$ of Section~\ref{sec:kr}. Its answers are
\[
\mathit{ans}(Q,\mathcal{K}) = \{\theta(\bar x) \mid \mathcal{I}_{\mathcal{A}}\models \varphi\theta\},
\]
where $\theta$ ranges over the assignments of values from their domains to $\bar x$ and $\bar y$, and $\models$ is first-order satisfaction. Atoms are evaluated by computing their terms and, for predicates, calling them. Every variable ranges over a finite domain, which may depend on the values of outer variables, so every query is safe. Negation is negation as failure: $\neg\varphi\theta$ holds if and only if $\varphi\theta$ is not satisfied in $\mathcal{I}_{\mathcal{A}}$. Because $\mathcal{I}_{\mathcal{A}}$ is a single finite interpretation of ground facts, this is Reiter's closed-world assumption~\cite{Reiter1978}. Evaluation enumerates answers with multiplicity, as SQL does; $\mathit{ans}(Q,\mathcal{K})$ is the set of distinct answers, which the \texttt{distinct} operator returns. Evaluation proceeds left to right by nested iteration over the variables' domains, binding each variable when it is first needed and abandoning a binding as soon as a conjunct fails.

\emph{Positive} queries, which select variables and whose condition uses only class and property atoms, equality, conjunction, disjunction and existential quantification, are monotone: adding facts to $\mathcal{A}$ never removes an answer. The remaining constructs, including aggregates, are deliberately closed-world. Without predicates, \ac{eql}'s conditions are first-order formulas under the active-domain semantics, in AC$^0$ in data complexity and PSPACE-complete in combined complexity~\cite{Vardi1982,immerman1987languages}; a query with $k$ variables over domains of size at most $d$ calls its predicates at most $|\varphi|\cdot d^{k}$ times.

\section{Ontomatic: Compiling OWL 2 RL Ontologies}
\label{sec:ontomatic}

Ontomatic turns an OWL ontology into a \ac{krrood} knowledge base in two phases. TBox compilation generates Python modules with classes, property descriptors and axioms. ABox loading creates the objects and materializes the consequences of the ontology. Ontomatic targets the OWL~2~RL profile~\cite{motik2012owl2profiles}. Entailment of assertions in OWL~2~RL is captured by a fixed set of first-order rules over RDF triples, the OWL~2~RL/RDF rules~\cite[Section~4.3]{motik2012owl2profiles}. Each rule is named by its kind (\texttt{eq} equality, \texttt{prp} properties, \texttt{cls} class expressions, \texttt{cax} class axioms, \texttt{dt} datatypes, \texttt{scm} the schema) and construct: \texttt{prp-dom} derives $C(x)$ from $P(x,y)$ if $P$ has domain $C$. For an RL ontology without punning and without annotation-property axioms, an assertion $C(a)$, $P(a,b)$ or $\mathit{SameIndividual}(a,b)$ is entailed if and only if it follows from the RL/RDF rules applied to the ontology's RDF translation~\cite[Theorem PR1]{motik2012owl2profiles}. Ontomatic realizes the rules with the mechanisms of Section~\ref{sec:kr}. It covers named classes with subclass and equivalence axioms; domains and ranges that are named classes; sub-, equivalent, symmetric and transitive properties, one inverse per property, and property chains; restrictions and intersections as superclasses; unions in subclass position; and one sufficient condition per class, a \texttt{someValuesFrom} or \texttt{hasValue} restriction with a named filler, possibly intersected with named classes. Of the property rules, the \emph{assign rules} \texttt{prp-spo1}, \texttt{prp-spo2}, \texttt{prp-eqp1/2}, \texttt{prp-inv1/2}, \texttt{prp-symp} and \texttt{prp-trp} are applied on every assignment, the others when loading. The rules that derive the equality of two individuals (functional and inverse-functional properties, keys, maximum cardinalities) or an inconsistency (disjointness, irreflexivity, asymmetry and others) are not applied but checked after loading, on object properties, except irreflexivity of symmetric, transitive properties. The supplementary material maps all 78 RL/RDF rules: 14 apply when loading, 9 on assignment, 15 by construction of the hierarchies, 21 are checked, 13 derive nothing new here, and 6 concern constructs outside this list.

\paragraph{TBox compilation}
Named classes become Python classes related by inheritance. Every object property becomes two things: a descriptor class, whose bases encode its super-properties and characteristics, and an attribute of its domain class, typed by its range. Domains and ranges that are not declared are derived from equivalent, inverse and super-properties, falling back to the ontology's root class; these derivations instantiate \texttt{prp-dom}, \texttt{prp-rng}, \texttt{prp-inv}, \texttt{prp-eqp}, \texttt{scm-dom2} and \texttt{scm-rng2} (supplement). These schema-level rules were built incrementally as a ripple-down rule base~\cite{compton2021rdr}. Class expressions that state sufficient conditions for membership become axioms. These are \texttt{hasValue} definitions (Listing~\ref{lst:axiom}) and class expressions in subclass position, such as $\texttt{Person}\sqcap\exists\texttt{loves}.\texttt{Sports}\sqsubseteq\texttt{SportsLover}$. Restrictions in superclass position state necessary conditions, which never make an individual a member of the class: they refine the types of attributes, and loading applies them to the members of the class. Classes whose instances may also belong to unrelated classes are generated as roles. The ontology marks them with a restriction on an auxiliary property \texttt{roleFor}, which we added to OWL2Bench for the classes that represent roles of a person or an organization.

\paragraph{ABox loading and materialization}
Ontomatic (Algorithm~\ref{alg:loading}) never changes the class of an object it has created, so it infers all types before any object exists. Steps~1 and~2 work on lightweight proxies of the individuals; step~2 also applies transitivity and chains to the properties that class expressions and chains use, and evaluates the axioms in a compiled Python form for speed. Step~3 creates the objects and their roles. Step~4 assigns each property value, asserted or required by a \texttt{hasValue} restriction, through its descriptor, on an object of the subject whose class declares the property and to an object of the value that fits its range. Each assignment triggers the assign rules, for asserted and inferred facts alike, until no new fact arises. Transitive properties that are also symmetric are an exception. Chaining them on every assignment is expensive (Section~\ref{sec:experiments}), so step~5 completes them at once: within each weakly connected component of such a property's graph, every pair of individuals is related. This is exact, because the transitive and symmetric closure of a graph relates exactly the members of each connected component; RDFox treats \texttt{owl:sameAs} similarly~\cite{motik2015sameas}. If the property has a super-property, an inverse, an equivalent property or occurs in a property chain, the facts added in this step are then propagated like any other fact. Otherwise they are stored directly, and their provenance is the component.

\begin{algorithm}[t]
\caption{ABox loading in Ontomatic (\texttt{OwlLoader.load}).}
\label{alg:loading}
\footnotesize
\begin{algorithmic}[1]
\Require RDF graph $G$ of the ABox, generated model
\State \textbf{for each} individual $i$ of $G$: $p_i \gets$ a proxy with the asserted types and values of $i$ and those implied by sub-, inverse and symmetric properties \Comment{Step 1}
\Repeat \Comment{Step 2}
  \State apply chains and transitivity where types depend on them
  \State \textbf{for each} proxy $p_i$: add the domains and ranges of its properties, the classes whose axioms it satisfies, and what the necessary conditions of its classes require
\Until{no type or value is added}
\State \textbf{for each} proxy $p_i$: $O_i \gets$ one object per most specific type \Comment{Step 3}
\State \textbf{for each} $P(i,j)$ asserted or required by \texttt{hasValue}: add the object of $O_j$ fitting $P$'s range to $P$ on the object of $O_i$ declaring $P$; the rules of $P$ fire \Comment{Step 4}
\State \textbf{for each} weakly connected component $C$ of a symmetric, transitive $P$: add $P(a,b)$ for all $a, b \in C$ \Comment{Step 5}
\State \Return the objects $O_i$
\end{algorithmic}
\end{algorithm}

\paragraph{What is preserved}
The loading procedure is sound with respect to OWL~2~RL:

\begin{proposition}[Soundness]
\label{prop:soundness}
Let $\mathcal{O}$ be an OWL~2~RL ontology without punning, and let $\mathcal{A}^*$ be the knowledge base that Ontomatic produces from it. Every class and property assertion of $\mathcal{I}_{\mathcal{A}^*}$ is entailed by $\mathcal{O}$. Consequently, every answer of a positive \acs{eql} query over $\mathcal{A}^*$ is a certain answer over $\mathcal{O}$.
\end{proposition}

Every fact that Algorithm~\ref{alg:loading} derives is the conclusion of a sequence of RL/RDF rules, including the schema-level domains and ranges. Positive queries are preserved under homomorphisms, and $\mathcal{I}_{\mathcal{A}^*}$ maps homomorphically into every model of $\mathcal{O}$, even one that identifies individuals that \ac{krrood} keeps apart.

\ac{krrood} does not merge individuals; the check after loading reports every application of an equality rule and of the checked inconsistency rules (supplement). Consistency is otherwise assumed, as rules such as \texttt{dt-not-type} and \texttt{cls-nothing2} are not checked. If no equality rule applies, no equality between distinct names is entailed, so keeping individuals apart loses no certain answer of a positive query, and the converse of Proposition~\ref{prop:soundness} holds:

\begin{proposition}[Completeness]
\label{prop:completeness}
Let $\mathcal{O}$ and $\mathcal{A}^*$ be as in Proposition~\ref{prop:soundness}, let $\mathcal{O}$ be consistent and use only the constructs listed above, with at most one value of a data property per individual, and let the check report no equality. Then every class assertion $C(a)$, with $C$ a named class, and every object- and data-property assertion entailed by $\mathcal{O}$ holds in $\mathcal{I}_{\mathcal{A}^*}$.
\end{proposition}

By Theorem PR1~\cite{motik2012owl2profiles}, it suffices that $\mathcal{A}^*$ is closed under the RL/RDF rules. The check rules out the equality rules. The property rules are applied to every fact, and the typing rules to every fact known in step~2, which closes the properties that class expressions and chains use. A later transitive fact relates individuals that already have facts of the property, so it adds no domain or range. Hence every certain answer over $\mathcal{O}$ of a positive \acs{eql} query holds in $\mathcal{I}_{\mathcal{A}^*}$, which contains every entailed assertion, and \ac{eql} returns it if every individual is denoted by one object and its roles (see Q12, Section~\ref{ssec:correctness}).

\paragraph{At runtime}
After loading, each assignment applies the assign rules. Class memberships are not derived at runtime. A class defined by a \texttt{hasValue} axiom is queried through that axiom, as the robot of Section~\ref{ssec:agent_loop} does for \texttt{T20CricketFan}; other axioms are evaluated only when loading.

\begin{proposition}[Runtime]
\label{prop:runtime}
Let $\mathcal{O}$ and $\mathcal{A}^*$ be as in Proposition~\ref{prop:soundness}, and let application code assert property facts by assignment. Every fact of the resulting knowledge base is entailed by $\mathcal{O}$ and the asserted facts. If every subject of an asserted or derived fact has an object that declares the fact's property, and equivalent properties have the same characteristics, its object-property assertions are closed under the assign rules, except transitivity of properties that are also symmetric.
\end{proposition}

The supplementary material proves both statements. An assignment applies every assign rule that has the new fact as a premise, joined with the facts present, and recurses on each new fact; for a rule application whose premises are present afterwards, the premise added last was propagated when all others were present. Symmetric, transitive properties are completed only by step~5, and at runtime a fact whose subject has no object declaring the property is not stored.

\section{ORMatic: Long-Term Memory}
\label{sec:ormatic}

An agent also keeps knowledge beyond the lifetime of its process, such as an episodic memory of what it has done~\cite{beetz2025robot}, often more than fits in working memory. ORMatic, \ac{krrood}'s persistence layer, is the agent's long-term memory. From the TBox's classes, it generates a relational schema, data access objects (DAOs) and conversions between objects and DAOs, so the domain model remains the single definition of the agent's knowledge, free of persistence code. Working memory and reasoning stay in the program's objects; the database is not a mirror of them and does not reason. It keeps what the agent chooses to store, such as an episode of a task with its inferences, for later use: the agent can recall it as objects and query it without loading it, and learning components can read its tables. The database adds indexes and a query optimizer~\cite{selinger1979access}.

An \ac{eql} query is a symbolic expression separate from its evaluation, so it can be evaluated in working memory or translated to SQL (Listing~\ref{lst:ormatic}). The translator maps a variable to the table of its class and an attribute chain to joins, here of \texttt{Student} with \texttt{Person} on the role taker. Every object property that Ontomatic generates is collection-valued, and such an attribute is stored as rows of an association table: ranging over its elements becomes a join, and membership and existential quantification become correlated \texttt{EXISTS} subqueries. Universal quantification, predicates and functions, which run Python code, and rules, which create objects, are rejected rather than translated with a different meaning. Asked to select identifiers, the translator returns the answers' IRIs instead of objects and joins only the tables whose columns a query reads or that restrict a variable to its class. We translated all 18 benchmark queries and evaluated them in PostgreSQL over the objects built from the benchmark's OWL~2~RL closure: every translation returns the same answers as \ac{eql} and GraphDB (Section~\ref{ssec:querying}).

\begin{lstlisting}[style=eql, float=h, caption={One \acs{eql} query evaluated in working memory and, translated by ORMatic, in long-term memory.}, label={lst:ormatic}]
s = variable(Student, domain=students)
over_25 = an(entity(s).where(s.has_age > 25))  # via role taker
in_memory = list(over_25.evaluate())              # working memory
stored = eql_to_sql(over_25, session).evaluate()  # long-term memory
\end{lstlisting}

\section{Experiments}
\label{sec:experiments}

We evaluate \ac{krrood} on knowledge compiled from an OWL~2~RL ontology. Correctness (Section~\ref{ssec:correctness}) tests whether the program's knowledge base is the one OWL~2~RL entails, so that reasoning in the program can replace an OWL~2~RL reasoner. Loading (Section~\ref{ssec:loading}) and querying (Section~\ref{ssec:querying}) test whether working and long-term memory cost about as much as established systems, so that the cost of the design is acceptable. The agent loop (Section~\ref{ssec:agent_loop}) measures what a single world model saves an agent that reasons and computes.

\paragraph{Setup}
We use the OWL~2~RL profile of OWL2Bench~\cite{singh2020owl2bench}, a benchmark of logical reasoning, with one university: 3,667 individuals and 54,901 explicit statements. Its closure, computed by GraphDB, has 1,431,635 statements. Of these, 1.42 million are assertions about individuals. This closure is the pre-reasoned input: knowledge whose inferences are already computed, as when an agent loads what it inferred earlier. Ontomatic generates the model from the ontology with our \texttt{roleFor} markers, and ORMatic stores the loaded objects in PostgreSQL.

We compare against six systems. GraphDB 11.2 Free, with its OWL~2~RL ruleset, gives the reference answers. RDFLib 7.4 uses the \texttt{owlrl} reasoner. Nemo 0.10.1~\cite{ivliev2024nemo} is a Datalog engine; we wrote its OWL~2~RL/RDF rules from the specification (supplement). reasonable 0.4.4 is an OWL~2~RL reasoner in Rust. Owlready2 0.49 and Protégé 5.6.7 both use the DL reasoner Pellet. GraphDB runs on one core, the limit of its Free license. All experiments ran on Ubuntu 24.04 with an Intel Core i7-13700 and 64\,GB of RAM, in Docker containers, except Protégé, a desktop application that we ran by hand.\footnote{The supplement's code, data and Docker set-up run every experiment but Protégé's.} GraphDB, RDFLib and Protégé load once; RDFLib is stopped after three hours. Memory is the increase of the peak resident set size of the process tree, or of the Java heap in use for GraphDB (8\,GB heap, separate load) and Protégé (28\,GB heap).

\subsection{Correctness}
\label{ssec:correctness}

We normalized each system's answers to sets of tuples of IRIs and literals and compared them with GraphDB's. RDFLib, Owlready2, \ac{eql} and SQL translated from \ac{eql} return answer sets identical to GraphDB's on all 18 queries. Protégé returns GraphDB's numbers of answers on the 16 queries it completes; it does not finish Q20 and raises an error on Q9. We also compared the knowledge base produced by Ontomatic with GraphDB's OWL~2~RL closure, assertion by assertion: for all 3,667 individuals, the class memberships and the object- and data-property assertions, 1.42 million in all, coincide, with none missing or extra. So does Nemo's closure; reasonable's differs by 70,248 assertions, as its release 0.4.4 does not implement the property-chain rule \texttt{prp-spo2} and it merges the 21 heads of organizations, applying \texttt{prp-ifp} to subjects with different objects. From the raw data of 2, 4 and 8 universities, \ac{krrood}'s knowledge base equals Nemo's closure as well, up to 142 million facts. Although OWL2Bench declares functional and inverse-functional properties, the check of Section~\ref{sec:ontomatic} finds no equality and no inconsistency, so no equality is entailed, and keeping individuals apart loses no certain answer of a positive query. The result agrees with Propositions~\ref{prop:soundness} and~\ref{prop:completeness}, although the benchmark lies just outside their conditions: OWL2Bench uses 47 IRIs both as classes and as individuals, and our \texttt{roleFor} markers lie outside OWL~2~RL, though they extend it conservatively (supplement).

While the robot of Section~\ref{ssec:agent_loop} runs, we compared the knowledge base after 0, 10, 50, 100 and 200 steps of five seeds with Nemo's closure of the raw data and the facts perceived so far. No fact is extra, and the property assertions coincide at every checkpoint, as Proposition~\ref{prop:runtime} states. Because class memberships are not derived at runtime (Section~\ref{sec:ontomatic}), the knowledge base lacks 235 to 325 entailed memberships per seed. These belong to \texttt{T20CricketFan}, which the robot queries through its axiom and so finds every fan, and to three classes whose axioms are evaluated only when loading.

Q12 shows the limit of roles. OWL2Bench entails that its seven research groups are persons, but no marker anticipates this. \ac{krrood} therefore gives each group a second object, a \texttt{Person} with an \texttt{Employee} role, that shares only the IRI. Q12 still returns GraphDB's answers. In general, however, \ac{eql} follows the semantics of Section~\ref{ssec:eql_semantics} only when each individual is one object plus its roles. All other OWL2Bench individuals are. Thus the program's knowledge base is the benchmark's closure, and its property assertions stay closed at runtime.

\subsection{An Agent Loop}
\label{ssec:agent_loop}

\paragraph{Purpose and scenario}
This experiment asks two questions. Can an agent whose knowledge changes every step, and is partly inferred and partly computed by its own code, work with a single world model in \ac{krrood}? And what does a second world model cost in code, writes, round trips and time, when all builds make the same decisions (Table~\ref{tab:integration}, Figure~\ref{fig:builds})? A delivery robot drives on the OWL2Bench campus, to which a map, one per seed, adds rooms and charging docks. In each of 200 steps of five seeds, it perceives three new facts, each an enrollment, a course taken or a new T20 cricket fan, and decides. A handout goes to a student of a requested college who takes a course in a room the robot can reach (Listing~\ref{lst:agent}); membership in the college is inferred by the chain $\texttt{enrollIn}\circ\texttt{isPartOf}\sqsubseteq\texttt{isMemberOf}$. A ticket goes to a \texttt{T20CricketFan} (Listing~\ref{lst:axiom}) whose mailbox the robot can reach. The robot drives to the nearest candidate or to a dock. Reachability and driving time come from its path planner, Dijkstra's algorithm, and change as it moves.




\paragraph{Builds}
With \ac{krrood} (Listing~\ref{lst:agent}, Figure~\ref{fig:builds}), perceiving is an assignment, whose property rules apply the chain at once, and each decision is one \ac{eql} query whose predicate \texttt{CanReach} and function \texttt{travel\_time} call the planner during evaluation. With GraphDB, a SPARQL update mirrors each step's facts into the store, which infers incrementally, and the IRIs that a SPARQL query returns are mapped back to objects and filtered with the planner. With GraphDB ``push'', SPARQL decides alone, so the planner's results for every room are written into the store before each query. Nemo, which cannot update a closure it has computed, recomputes the closure from the raw data and a file of the perceived facts each step, and Datalog rules select the candidates. With Owlready2, perceiving is an assignment on its objects, proxies of a quadstore, and infers nothing; Pellet is run every step, and a search returns the candidates, filtered with the planner. In Table~\ref{tab:integration}, \emph{sync.\ lines} are code that only keeps two world models in agreement.


\paragraph{Results}
All builds take the same action in every step of every seed (Owlready2: one seed). \ac{krrood} needs one world model and no synchronization; GraphDB needs a second world model, with synchronization code, writes and round trips every step, and letting SPARQL decide alone raises the writes per step from 4 to 405. Using one language does not remove the second world model. The Owlready2 build is written only in Python, yet every step it deletes its inferences, exports its quadstore to Pellet and writes 1.4 million inferences back, taking 33\,s. \ac{krrood} and GraphDB have comparable step times, 90 and 96\,ms: \ac{krrood}'s is spent in its query (88\,ms, against GraphDB's 7.5\,ms), GraphDB's in its update (89\,ms; 38\,ms when empty). Nemo spends its step recomputing the closure. reasonable (not in Table~\ref{tab:integration}) returns its whole closure every step and takes 4.6\,s. It misses every handout, because it does not apply the chain that infers college membership.

\section{Discussion and Conclusion}
\label{sec:discussion_conclusion}

On OWL2Bench, \ac{krrood} turns an agent's program into a knowledge base that equals an OWL~2~RL reasoner's closure from one to eight universities, at costs comparable to established systems, and a robot built on it needs one world model and decides like ones built on GraphDB, Nemo or Owlready2.

\paragraph{Limitations}
\ac{krrood} adopts the closed-world and unique-name assumptions, so where Proposition~\ref{prop:completeness} does not apply, an answer can contradict OWL entailment, and partial, noisy observation challenges this reading. At runtime, class memberships are not derived, axioms of class expressions other than \texttt{hasValue} are not yet evaluated, and inferred facts are not retracted. \ac{eql}'s rules are not recursive, and it has no query planner. Ontomatic covers part of OWL~2~RL (Section~\ref{sec:ontomatic}), a data attribute holds one value, roles need markers, and an unforeseen multiple classification splits an individual. We evaluated one benchmark, up to eight universities, and one agent. We will maintain inferences incrementally~\cite{MotikNenovPiroHorrocks2015}, add a query planner, and evaluate \ac{krrood} on real robots and with several agents that share long-term memory.
