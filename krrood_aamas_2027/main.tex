\begin{abstract}
Robots and other autonomous agents are built on cognitive architectures, whose modules for perception, planning, control and learning are object-oriented programs that act on shared knowledge. When this knowledge is modeled in an ontology, it lives in a second representation, which an external reasoner processes under different assumptions about completeness, naming and consistency, and which must be kept synchronized with the program. We present KRROOD, a framework in which the agent's object-oriented program is its knowledge base: classes and property descriptors form the terminology, live objects form the assertions, and property rules fire when facts are asserted. The Entity Query Language (EQL) queries the program with a formal, closed-world semantics. Its predicates and functions are the agent's own procedures, so reasoning is not limited to ontological inference. Ontomatic compiles OWL~2~RL ontologies into such programs by realizing a subset of the OWL~2~RL inference rules, so that positive queries return only answers entailed by the ontology and, under conditions we identify, all of them. ORMatic maps the same classes to a relational database that serves as the agent's long-term memory, and translates a subset of EQL to SQL. On the OWL2Bench benchmark, KRROOD returns the same answers as an OWL~2~RL reasoner on all 18 queries of the RL profile, and its knowledge base matches the reasoner's class memberships and property assertions exactly. We also compare loading and reasoning time, memory use and query time with established OWL and RDF systems.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Robots and other autonomous agents are built on cognitive architectures, which organize perception, planning, control and learning into modules that share knowledge about the world and the task~\cite{langley2009cognitive,kotseruba2020cognitive}. In robotics, ontologies in the Web Ontology Language (OWL) are a common way to make this knowledge explicit, shareable and open to sound inference~\cite{olivares2019review,Tenorth2013,delgrande2024current}. The modules themselves, however, are object-oriented programs: perception produces objects, and planners and controllers manipulate them~\cite{beetz2025robot}. For the developer of such an agent, the practical value of an ontology therefore depends on how well it integrates with the agent's \emph{application code}, the program that perceives, decides and acts~\cite{toberg2024commonsense}.

Today this integration means maintaining two representations of the same world: the objects of the program and the individuals of the ontology. The two differ in three fundamental assumptions. OWL assumes an open world, in which a missing fact is unknown, whereas programs and databases treat their data as complete~\cite{Reiter1978}. OWL does not assume that different names denote different individuals, whereas distinct objects are distinct. And in OWL an inconsistency makes every statement entailed, whereas a program treats a violated constraint as an error to be handled~\cite{motik2009bridging}. The developer has to translate between the two representations, invoke a reasoner on an exported copy of the data and map the results back. This is an object-ontological counterpart of the object-relational impedance mismatch~\cite{ireland2015exposing,ledvinka2020comparison}.

A second requirement comes from the agent itself. Much of what a robot needs to know is not stated but computed from its own data. Whether an object is on a table, for instance, follows from the poses that perception estimates. KnowRob therefore attaches procedures, called computables, to the predicates of its knowledge base~\cite{Tenorth2013}. A knowledge representation for such agents has to let reasoning call the agent's own code.

This paper argues that ontological knowledge can instead be \emph{compiled into the agent's program}, so that the program itself becomes the knowledge base and its procedures take part in reasoning. We present \acf{krrood}, a Python framework built on this idea (Figure~\ref{fig:arch}). Classes and property descriptors form the terminological part of the knowledge base (the TBox) and the live objects its assertional part (the ABox). Property rules fire at the moment application code asserts a fact. A query language with a formal, closed-world semantics reasons over the objects directly, and its predicates and functions are ordinary Python callables, so reasoning in \ac{krrood} is not limited to ontological inference. A query is a symbolic expression that is separate from its evaluation: by default it is evaluated over the objects in memory, and a subset of \ac{eql} can also be translated to SQL and evaluated by a database. We compare \ac{krrood} with OWL~2~RL reasoners to benchmark its ontological reasoning and to position it in the literature, not because OWL~2~RL bounds what it can express. The argument applies to any object-oriented language. We use Python because it is the common language of robotics and machine learning, and because its operator overloading and introspection allow a query language to be embedded in it. We make five contributions:

\begin{enumerate}
\item An object-oriented knowledge representation with a formal reading as a knowledge base, in which properties are first-class descriptors that carry their logical characteristics, multiple classification is handled by roles, and predicates are computed by the agent's own code (Section~\ref{sec:kr}).
\item The \acf{eql}, a query language embedded in Python, with a formal semantics that places it in known complexity classes, and in which class axioms and rules are ordinary query conditions (Section~\ref{sec:eql}).
\item Ontomatic, which compiles OWL~2~RL ontologies into such programs by realizing a subset of the OWL~2~RL inference rules, so that positive queries return only answers entailed by the ontology and, under conditions we identify, all of them (Section~\ref{sec:ontomatic}).
\item ORMatic, which generates a relational database schema from the same classes as the agent's long-term memory and translates a subset of \ac{eql} to SQL, so that queries over stored knowledge can use the optimizations of a database system (Section~\ref{sec:ormatic}).
\item An evaluation on the OWL2Bench benchmark~\cite{singh2020owl2bench} that compares answers, loading and reasoning time, memory use and query time with established OWL and RDF systems (Section~\ref{sec:experiments}).
\end{enumerate}

Source code and experiment scripts are provided as anonymized supplementary material.

\section{Related Work}
\label{sec:related-work}

\paragraph{Object-ontology mapping}
Several libraries give programs access to ontologies, differing in what a program object is. In the OWL API~\cite{horridge2011owl}, objects represent axioms and class expressions rather than domain entities. Jastor~\cite{szekely2009jastor}, the mapping of Kalyanpur et al.~\cite{kalyanpur2004automatic}, KOMMA~\cite{wenzel2010komma} and JOPA~\cite{ledvinka2016jopa} generate or annotate Java classes whose instances stand for individuals, while the ontology store remains the authoritative copy. Puleston et al.\ compare such approaches and argue for hybrid models in which part of the knowledge stays in the ontology~\cite{puleston2008integrating}. In Python, Owlready2~\cite{lamy2017owlready} creates classes from an ontology at load time and stores individuals in a quadstore. OWLAPY~\cite{baci2025owlapy} and OWLOOP~\cite{buoncompagni2024owloop} model OWL entities and axioms as Python or object-oriented constructs. In all of these, the ontology defines the program's classes, and reasoning is delegated to an external reasoner whose results are read back. \ac{krrood} reverses the direction: the classes of application code are the knowledge base, an ontology is one way of generating them, and inference and queries run inside the program.

\paragraph{Reasoners and materialization}
OWL reasoners such as Pellet~\cite{sirin2007pellet}, HermiT~\cite{glimm2014hermit} and RacerPro~\cite{haarslev2012racerpro} decide entailment for expressive description logics. Rule-based systems such as RDFox~\cite{nenov2015rdfox} and GraphDB materialize the consequences of OWL~2~RL with Datalog-style rules, building on description logic programs~\cite{grosof2003description}. These systems operate on their own stores, so applications export their state, invoke the reasoner and parse the results. \ac{krrood} materializes RL consequences too, but in the objects of application code, and property consequences at the time facts are asserted. Its queries are then evaluated under the closed-world assumption, the database-style reading that Motik et al.~\cite{motik2009bridging} and Tao et al.~\cite{tao2010integrity} give to the constraints that developers write in OWL.

\paragraph{Queries and rules in the host language}
LINQ integrates queries over objects, relations and XML into .NET languages~\cite{meijer2006linq}. Python libraries embed Datalog or probabilistic logic programs~\cite{carbonnelle2020pydatalog,dries2015problog2} but do not query the program's own objects. ErgoAI~\cite{kifer2018ergoai} offers object-oriented logic programming through F-logic~\cite{kifer1995flogic}, in which objects, classes and attributes are terms of the logic. KnowRob~\cite{Tenorth2013,beetz2018know} reasons in Prolog over a robot's OWL knowledge base and attaches procedures, called computables, that compute facts from the robot's data when a query needs them. Both keep the knowledge in a logic language, outside the language of application code. \ac{eql} combines the embedding of LINQ with a first-order query language and rules over the program's own objects.

\paragraph{Ontologies in agent programming}
In multi-agent systems, JADE maps agent-communication content to Java classes generated from an ontology~\cite{bellifemine2007jade,caire2010jadeontology}. AgentSpeak-DL~\cite{moreira2006agentspeakdl} and JASDL~\cite{klapiscak2009jasdl} combine belief--desire--intention (BDI) agents with description-logic reasoning over their belief bases. Recent work observes that BDI frameworks still lack convenient support for ontological beliefs. It calls for ontology triples in the belief base, ontological inference during deliberation and queries over beliefs~\cite{burattini2025gap}, and proposes mappings between triples and beliefs~\cite{longo2025t2b2t}. \ac{krrood} addresses these requirements for agents written in Python: the belief base is the program's objects, and inference and queries operate on it directly.

\section{Knowledge Representation in KRROOD}
\label{sec:kr}

In \ac{krrood}, the knowledge base of an agent is its object-oriented program. We use one running example throughout the paper: an assistant agent for a university whose knowledge comes from the OWL2Bench university ontology~\cite{singh2020owl2bench}. The agent's \emph{application code} manipulates \texttt{Person}, \texttt{Student} and \texttt{Course} objects, for instance to suggest courses to a student, and these same objects are the individuals of its knowledge base.

\paragraph{Vocabulary}
A \ac{krrood} knowledge base is a pair $\mathcal{K}=(\mathcal{T},\mathcal{A})$. The TBox $\mathcal{T}$ consists of Python declarations of four kinds:
\begin{itemize}
  \item \emph{Concepts} are classes. Subsumption between named concepts is declared by inheritance, and \texttt{issubclass} computes its reflexive-transitive closure.
  \item \emph{Properties} (binary relations) are attributes. Each attribute is managed by a \emph{property descriptor}, a class whose position in the descriptor hierarchy encodes property subsumption (\texttt{IsCrazyAbout} $\sqsubseteq$ \texttt{Loves} $\sqsubseteq$ \texttt{Likes}) and whose \emph{mixins}, base classes that each add one behavior to the classes inheriting from them, encode property characteristics such as transitivity, symmetry, inverses and property chains.
  \item \emph{Axioms} that typing and inheritance cannot express, such as class definitions, are class methods that return an \ac{eql} condition (Section~\ref{sec:eql}) characterizing the members of the class. Because $\mathcal{K}$ has a single interpretation (below), an axiom does not constrain models as in a description logic. It is a condition that can be checked, like an integrity constraint~\cite{motik2009bridging,tao2010integrity}, or used to classify individuals (Section~\ref{sec:ontomatic}).
  \item \emph{Predicates and symbolic functions} are Python callables that can appear as atoms of \ac{eql} conditions. They give reasoning direct access to the agent's own procedures, such as the timetable check of Listing~\ref{lst:agent}.
\end{itemize}
The ABox $\mathcal{A}$ consists of the live objects and their attribute values, which form the agent's \emph{working memory}. Listing~\ref{lst:kr} shows part of the running example. Its last statement attaches a descriptor to a class attribute: from then on, every read and write of \texttt{is\_crazy\_about} on a \texttt{Person} passes through \texttt{IsCrazyAbout}, which applies the property's rules.\footnote{Listings are simplified. Listing~\ref{lst:loading} and the experiments use an earlier version of \acs{krrood}, the other listings the current one; the supplementary material contains both.}

\begin{lstlisting}[style=eql, caption={Part of the running example. Classes are concepts, attributes are properties, and descriptor classes carry property semantics.}, label={lst:kr}]
@dataclass(eq=False)
class Person(Thing):
    is_crazy_about: set[Interest]

@dataclass(eq=False)
class Student(Role[Person]):  # played by a Person
    takes_course: set[Course]

class Loves(Likes): ...
class IsCrazyAbout(Loves): ...  # sub-property
class IsPartOf(PropertyDescriptor, TransitiveProperty): ...

# IsCrazyAbout manages Person.is_crazy_about
Person.is_crazy_about = IsCrazyAbout(Person,
                                     "is_crazy_about")
\end{lstlisting}

\paragraph{Multiple classification through roles}
OWL allows an individual to belong to several classes that are not related by subsumption, such as a person who is both a \texttt{Student} and a \texttt{SportsFan}. A Python object, however, has a single most specific class. \ac{krrood} resolves this with the Role pattern~\cite{steimann2000roles,Guarino2004,boella2007roles}, and in this paper ``role'' refers only to this pattern: a role is an object of its own class that refers to the entity playing it, its \emph{role taker}, and delegates to it reads of every attribute it does not declare itself (\texttt{Student} in Listing~\ref{lst:kr}). A student who is also a sports fan is one \texttt{Person} object with a \texttt{Student} role and a \texttt{SportsFan} role, so the individual keeps a single identity.

\paragraph{Interpretation}
$\mathcal{K}$ has a single interpretation $\mathcal{I}_{\mathcal{A}}$, which assigns a set of individuals to every concept and a set of pairs to every property. Objects and individuals do not correspond one to one, because a role object and its role taker stand for the same individual. We therefore write $\iota(o)$ (iota) for the individual that an object $o$ denotes: a role object denotes the individual of its role taker, an object created for an ontology individual denotes the individual named by its IRI, and every other object denotes an individual of its own. On data values, such as numbers and strings, $\iota$ is the identity. With $O$ the set of objects in memory, a concept $C$ denotes $C^{\mathcal{I}}=\{\iota(o)\mid o\in O \text{ is an instance of } C\}$. A property $P$ that manages attribute $p$ relates the individual of every object to the individual of every value of its attribute: $P^{\mathcal{I}}=\{(\iota(o),\iota(v))\mid o\in O,\ v \text{ is } o.p \text{ or an element of } o.p\}$. A predicate denotes the tuples for which its code returns true, and a symbolic function the function its code computes. Their extensions are not stored in $\mathcal{A}$ but computed when a query needs them, like the computables of KnowRob~\cite{Tenorth2013}. $\mathcal{K}$ is read under the assumptions of relational databases~\cite{Reiter1978}:
\begin{itemize}
  \item \emph{closed world}: a ground atom, such as $\texttt{Student}(\mathit{alice})$, is false unless $\mathcal{I}_{\mathcal{A}}$ makes it true, so nothing is unknown;
  \item \emph{domain closure}: there are no individuals other than those that objects denote;
  \item \emph{unique names}: two objects denote the same individual only if they carry the same IRI or one is a role, possibly of a role, of the other.
\end{itemize}
These are the assumptions under which application code already treats its objects. OWL, in contrast, assumes an open world and does not assume unique names; Section~\ref{sec:ontomatic} shows how the two are reconciled for ontological knowledge.

\paragraph{Reasoning inside the program}
Knowledge in $\mathcal{K}$ is used in two ways. First, property descriptors apply the consequences of a fact at the moment application code asserts it: assigning a value to an attribute triggers forward chaining over the descriptor's characteristics. For example, adding T20 cricket to \texttt{p.is\_crazy\_about} also adds it to \texttt{p.loves} and \texttt{p.likes}. Class membership is derived when knowledge is loaded (Section~\ref{sec:ontomatic}) or by rules on request (Section~\ref{sec:eql}). Every inferred fact records the rule and the facts that produced it, so conclusions can be explained. Second, querying $\mathcal{K}$, including evaluating axioms, is done with \ac{eql}, which we present next. Section~\ref{sec:ontomatic} shows how both are generated from an OWL ontology.

\section{EQL: Querying the Program as a Knowledge Base}
\label{sec:eql}

\ac{eql} is a declarative query language embedded in Python. An \ac{eql} query is not a string passed to an external engine, as in SQL or SPARQL, but a Python expression built from symbolic variables. Its names and types can therefore be checked by the development environment, and it is evaluated directly over live objects without translating them into another representation. This continues the idea of language-integrated queries~\cite{meijer2006linq}, adding first-order formulas, negation as failure, quantifiers, rules and user-defined predicates. A complete formal treatment of syntax, semantics and complexity is part of the supplementary material; here we give the parts needed to read the paper.

\subsection{Syntax}
\label{ssec:eql_syntax}

\paragraph{Variables and terms}
A variable \texttt{x = variable(C, domain=D)} is a symbol ranging over the instances of class $C$ in a finite collection $D$. If $D$ is omitted, it is the set of all known instances of $C$. Because $D$ can be any collection computed by the program, a query can be restricted to the task-relevant part of the knowledge base. Terms are built from constants, variables, attribute access \texttt{t.a}, indexing \texttt{t.a[i]}, method calls \texttt{t.m($\bar t$)} and symbolic functions \texttt{f($\bar t$)}. Chains of attribute accesses replace the joins of relational query languages.

\paragraph{Atoms and formulas}
An atom is a predicate applied to terms, $p(\bar t)$, a comparison $t_1 \mathbin{\mathsf{op}} t_2$ with $\mathsf{op}\in\{=,\neq,<,\le,>,\ge,\in\}$, or a Boolean-valued term. Formulas are built by
\[
\varphi ::= \alpha \mid \varphi\wedge\varphi \mid \varphi\vee\varphi \mid \neg\varphi \mid \exists x\in D.\,\varphi \mid \forall x\in D.\,\varphi ,
\]
written as several arguments of \texttt{where}, \texttt{or\_}, \texttt{not\_}, \texttt{exists} and \texttt{for\_all}. The domain of a quantified variable may depend on outer variables. For example, \texttt{flat\_variable(s.takes\_course)} ranges over the courses of each student $s$.

\paragraph{Queries}
A query selects one or more variables, \texttt{entity(x)} or \texttt{set\_of(x, y)}, constrained by \texttt{.where($\varphi$)}, and is wrapped in a result quantifier. \texttt{an} accepts any number of answers. \texttt{the} requires exactly one, following Russell's definite description, and raises an error otherwise. Aggregates (\texttt{count}, \texttt{sum}, \texttt{max}, \dots) with \texttt{grouped\_by} and \texttt{having} correspond to the grouping operator of relational algebra.

Listing~\ref{lst:q22} shows OWL2Bench query Q22, ``students who take a course taught by the dean of an organization'', in SPARQL and in \ac{eql}. Each triple pattern becomes an attribute chain or a membership atom: no join keys are written, and the only join is the membership atom. The variable \texttt{s} ranges over a collection \texttt{students} computed by the program.

\begin{lstlisting}[style=eql, caption={OWL2Bench query Q22 in SPARQL (top) and \acs{eql} (bottom).}, label={lst:q22}]
SELECT ?s ?c WHERE { ?s a :Student .
  ?o a :Organization . ?o :hasDean ?d .
  ?d :teachesCourse ?c . ?s :takesCourse ?c }
\end{lstlisting}
\vspace{-0.9\baselineskip}
\begin{lstlisting}[style=eql]
s = variable(Student, domain=students)
o = variable(Organization)
dean = flat_variable(o.has_dean)
c = flat_variable(dean.teaches_course)
q22 = an(set_of(s, c).where(contains(s.takes_course, c)))
\end{lstlisting}

\paragraph{Axioms and rules}
Since an axiom is a class method returning an \ac{eql} condition, it can be inspected, used as a constraint, or used as the body of a rule. Listing~\ref{lst:axiom} shows the OWL2Bench definition $\texttt{T20CricketFan}\equiv\exists\texttt{isCrazyAbout}.\{\texttt{T20Cricket}\}$ as an axiom, and a rule that derives a \texttt{T20CricketFan} role for every person satisfying it. In general, a rule \texttt{inference(H)($\bar k$)} derives an instance of class $H$ for each answer of its body. Like a Skolem term, a derived object is identified by its class and its arguments. Evaluating the rule again, or another rule with the same class and arguments, returns the same object, so rule evaluation is idempotent. A rule is evaluated on request, like a query, and the application decides whether to add the derived objects to $\mathcal{A}$.

\begin{lstlisting}[style=eql, caption={An OWL class definition as an axiom, used as the body of a classification rule.}, label={lst:axiom}]
@dataclass(eq=False)
class T20CricketFan(SportsFan):
    @classmethod
    def axiom(cls, p):
        return contains(p.is_crazy_about, T20_CRICKET)

p = variable(Person)
fan = inference(T20CricketFan)(role_taker=p)
fans = an(entity(fan).where(T20CricketFan.axiom(p)))
\end{lstlisting}

\paragraph{A step of the agent}
Listing~\ref{lst:agent} puts these pieces together in one step of the university assistant. Application code asserts an observed enrolment, which triggers the property rules, and an \ac{eql} query then suggests courses that the student does not take and that fit her timetable. The timetable check is an ordinary Python function used as a predicate.

\begin{lstlisting}[style=eql, caption={A step of the assistant agent: assert an observation, then decide with a query that calls a domain procedure.}, label={lst:agent}]
@symbolic_function
def clashes(course, courses):
    return any(course.slot == o.slot for o in courses)

alice.takes_course.add(algebra)       # perceive
c = variable(Course, domain=offered)  # decide
suggestions = an(entity(c).where(
    not_(contains(alice.takes_course, c)),
    not_(clashes(c, alice.takes_course))))
\end{lstlisting}

\subsection{Semantics}
\label{ssec:eql_semantics}

A query $Q(\bar x)\leftarrow\varphi(\bar x,\bar y)$ is evaluated in the single interpretation $\mathcal{I}_{\mathcal{A}}$ of Section~\ref{sec:kr}. Its answers are
\[
\mathit{ans}(Q,\mathcal{K}) = \{\theta(\bar x) \mid \mathcal{I}_{\mathcal{A}}\models \exists\bar y.\,\varphi\theta\},
\]
where $\theta$ ranges over the assignments of values from their domains to $\bar x$, and $\models$ is first-order satisfaction. Atoms are evaluated by computing their terms and, for predicates, calling them. Every variable ranges over a finite domain, which may depend on the values of outer variables, so every query is safe. Negation is negation as failure: $\neg\varphi\theta$ holds if and only if $\varphi\theta$ is not satisfied in $\mathcal{I}_{\mathcal{A}}$. Because $\mathcal{I}_{\mathcal{A}}$ is a single finite interpretation of ground facts, this is Reiter's closed-world assumption~\cite{Reiter1978}. As in SQL, answers are produced with bag semantics, and \texttt{distinct} removes duplicates. Evaluation proceeds left to right by nested iteration over the variables' domains, binding each variable when it is first needed and abandoning a binding as soon as a conjunct fails.

Two properties of this semantics matter for the rest of the paper. First, \emph{positive} queries, which use only class and property atoms, equality, conjunction, disjunction and existential quantification, are monotone: adding facts to $\mathcal{A}$ never removes an answer. Second, the remaining constructs are deliberately closed-world. A query for students who take at most one course counts the courses in $\mathcal{A}$, whereas an OWL reasoner cannot conclude that a student takes at most one course without knowing all of them.

\subsection{Complexity}
\label{ssec:eql_complexity}

Table~\ref{tab:complexity} summarizes the complexity of evaluating \ac{eql} queries. \emph{Data complexity} fixes the query and measures cost in the size of $\mathcal{A}$, which is what matters for a deployed agent. \emph{Combined complexity} lets the query vary as well. Unions of conjunctive queries have the classical bounds~\cite{ChandraMerlin1977,AbiteboulHullVianu1995}. With negation and universal quantification, \ac{eql} conditions express first-order logic under the active-domain semantics, which is PSPACE-complete in combined complexity~\cite{Vardi1982} and in AC$^0$ in data complexity~\cite{immerman1987languages,barrington1990uniformity}. Counting aggregates raise data complexity to TC$^0$~\cite{hella2001aggregate}. Predicates and symbolic functions are arbitrary Python code, so we treat them as oracles. A query $\varphi$ with $k$ variables, including quantified ones, over domains of size at most $d$ calls them at most $|\varphi|\cdot d^{k}$ times. Evaluation therefore runs in polynomial time in the size of $\mathcal{A}$ whenever the callables run in polynomial time and return results of polynomial size. Termination of arbitrary callables cannot be guaranteed. The bounds concern queries; rules (Section~\ref{ssec:eql_syntax}) are evaluated as single queries.

\section{Ontomatic: Compiling OWL 2 RL Ontologies}
\label{sec:ontomatic}

Ontomatic turns an OWL ontology into a \ac{krrood} knowledge base in two phases. TBox compilation generates Python modules with classes, property descriptors and axioms. ABox loading creates the objects and materializes the consequences of the ontology. Ontomatic targets the OWL~2~RL profile~\cite{motik2012owl2profiles}, which was designed for rule-based implementations and builds on description logic programs~\cite{grosof2003description}. The semantics of OWL~2~RL is captured by a fixed set of first-order rules over RDF triples, the OWL~2~RL/RDF rules~\cite[Section~4.3]{motik2012owl2profiles}. The specification names each rule by what it reasons about (\texttt{eq} equality, \texttt{prp} properties, \texttt{cls} class expressions, \texttt{cax} class axioms, \texttt{dt} datatypes, \texttt{scm} the schema) and by the construct it handles. For example, \texttt{prp-dom} states that if $P$ has domain $C$ and $P(x,y)$ holds, then $C(x)$ holds, and \texttt{prp-spo1} that a fact of a sub-property is also a fact of its super-property. For an RL ontology without punning and without annotation-property axioms, an assertion $C(a)$, $P(a,b)$ or $\mathit{SameIndividual}(a,b)$ is entailed if and only if it follows from the RL/RDF rules applied to the ontology's RDF translation~\cite[Theorem PR1]{motik2012owl2profiles}. Ontomatic realizes the rules with the mechanisms of Section~\ref{sec:kr}. Table~\ref{tab:rl} lists the correspondence, including the rules that \ac{krrood} does not apply but checks after loading.

\paragraph{TBox compilation}
Every named class becomes a Python class, and \texttt{subClassOf} between named classes becomes inheritance. Every object property becomes a descriptor class, whose bases encode its super-properties and characteristics. It also becomes an attribute of its domain class, typed by its range. Domains and ranges that are not declared are derived from equivalent, inverse and super-properties, falling back to the ontology's root class. These schema-level rules were built incrementally as a ripple-down rule base~\cite{compton2021rdr}. Class expressions that state sufficient conditions for membership become axioms. These are \texttt{hasValue} definitions (Listing~\ref{lst:axiom}) and class expressions in subclass position, such as $\texttt{Person}\sqcap\exists\texttt{loves}.\texttt{Sports}\sqsubseteq\texttt{SportsLover}$. Restrictions in superclass position state necessary conditions. They refine the types of attributes, and loading applies them to the members of the class (Table~\ref{tab:rl}), but they never make an individual a member of the class. Classes whose instances may also belong to unrelated classes are generated as roles. The ontology marks them with a restriction on an auxiliary property \texttt{roleFor}, which we added to OWL2Bench for the classes that represent roles of a person or an organization.

\paragraph{ABox loading and materialization}
Listing~\ref{lst:loading} shows the loading procedure. An object's class cannot change after it is created, so all types are inferred before any object exists. Step~1 reads every individual into a lightweight proxy, with its asserted types and property values, and adds the values implied through sub-, equivalent, inverse and symmetric properties. Step~2 adds the domains and ranges of these properties, the classes whose axioms the proxy satisfies, and the types and values that the necessary conditions of its classes require. It also applies transitivity and chains to the properties that class expressions and chains use, and repeats until nothing new arises. Ontomatic evaluates the axioms in a compiled Python form for speed. Step~3 creates the objects. An individual that is, for example, both a \texttt{Student} and a \texttt{SportsFan} becomes one \texttt{Person} object with two role objects. Step~4 assigns each property value, asserted or required by a \texttt{hasValue} restriction, through its descriptor, on an object of the subject whose class declares the property and to an object of the value that fits its range. Each assignment triggers the property rules of Table~\ref{tab:rl}, for asserted and inferred facts alike, until no new fact arises. Transitive properties that are also symmetric are an exception. Chaining them eagerly is expensive (Section~\ref{sec:experiments}), so step~5 completes them at once: within each weakly connected component of such a property's graph, every pair of individuals is related. This step is exact: the transitive and symmetric closure of a graph relates every two members of each connected component, and each member to itself, and nothing else. If the property has a super-property, an inverse, an equivalent property or occurs in a property chain, the facts added in this step are then propagated like any other fact. Otherwise they are stored directly, and their provenance is the component.

\begin{lstlisting}[style=eql, float=t, caption={ABox loading in Ontomatic, simplified from \texttt{OwlLoader.load}. Comments name the steps.}, label={lst:loading}]
def load(graph, model):
    # 1. a proxy per individual, with its asserted
    #    types and values, plus the values implied by
    #    sub-, equivalent, inverse, symmetric properties
    proxies = {i: Proxy(i, graph.types(i), graph.values(i))
               for i in graph.individuals()}
    for x in proxies.values():
        x.add_implied_values(model)
    # 2. types from domains, ranges, axioms, necessary
    #    conditions, and values derived by chains and
    #    transitivity, repeated until nothing new arises
    while any([x.add_inferred_types(model)
               for x in proxies.values()]):
        pass
    # 3. an object per most specific type: a role taker
    #    and its roles share the individual's identity
    objects = {i: model.create(x.most_specific_types())
               for i, x in proxies.items()}
    # 4. assign asserted values and those required by
    #    hasValue restrictions; descriptor rules fire
    for s, p, o in chain(graph.property_assertions(),
                         model.required_values(objects)):
        subject = declaring(objects[s], p)
        getattr(subject, p).add(fitting(objects[o], p))
    # 5. close symmetric and transitive properties
    for P in model.symmetric_transitive_properties():
        for c in weakly_connected_components(P.graph()):
            for a, b in product(c, c):
                P.add_inferred(a, b)
    return objects
\end{lstlisting}

\paragraph{What is preserved}
The loading procedure is sound with respect to OWL~2~RL:

\begin{proposition}[Soundness]
\label{prop:soundness}
Let $\mathcal{O}$ be an OWL~2~RL ontology without punning, and let $\mathcal{A}^*$ be the knowledge base that Ontomatic produces from it. Every class and property assertion of $\mathcal{I}_{\mathcal{A}^*}$ is entailed by $\mathcal{O}$. Consequently, every answer of a positive \acs{eql} query over $\mathcal{A}^*$ is a certain answer over $\mathcal{O}$.
\end{proposition}

The first statement holds because every fact that Listing~\ref{lst:loading} derives is the conclusion of an RL/RDF rule of Table~\ref{tab:rl}, or of a sequence of them. This includes the schema-level derivation of domains and ranges, which only composes \texttt{prp-dom}, \texttt{prp-rng}, \texttt{prp-inv} and \texttt{prp-eqp}. The second statement holds because positive queries are preserved under homomorphisms, and $\mathcal{I}_{\mathcal{A}^*}$ maps homomorphically into every model of $\mathcal{O}$, including models that identify individuals that \ac{krrood} keeps apart. For an inconsistent $\mathcal{O}$ the guarantee is vacuous; the check described next reports the inconsistencies that the RL/RDF rules derive from $\mathcal{A}^*$.

\ac{krrood} does not merge individuals. Instead, a check after loading evaluates on $\mathcal{A}^*$ the RL/RDF rules that derive the equality of two individuals (\texttt{prp-fp}, \texttt{prp-ifp}, \texttt{prp-key}, \texttt{cls-maxc2}, \texttt{cls-maxqc3/4}) or an inconsistency (Table~\ref{tab:rl}), and reports every application. If none applies and $\mathcal{O}$ uses only the constructs of Table~\ref{tab:rl}, the unique-name assumption is entailed rather than assumed, and the converse of Proposition~\ref{prop:soundness} holds:

\begin{proposition}[Completeness]
\label{prop:completeness}
Let $\mathcal{O}$ and $\mathcal{A}^*$ be as in Proposition~\ref{prop:soundness}, let $\mathcal{O}$ use only the constructs of Table~\ref{tab:rl}, and let the check report no equality and no inconsistency. Then every class assertion $C(a)$, with $C$ a named class, and every object- and data-property assertion entailed by $\mathcal{O}$ holds in $\mathcal{I}_{\mathcal{A}^*}$.
\end{proposition}

By Theorem PR1, such an assertion follows from the RL/RDF rules, so it suffices that $\mathcal{A}^*$ with the reflexive \texttt{sameAs} facts is closed under them. By the check, no equality or inconsistency rule applies. The property rules are applied to every fact, and the typing rules to every fact known in step~2, which closes the properties that class expressions and chains use. A fact derived later by transitivity relates two individuals that already have facts of the property, so it adds no domain or range. Every fact is stored on an object that declares the property, which exists because step~2 typed the subject with the property's domain.

Queries that use negation, universal quantification or aggregation are evaluated under the closed-world reading of Section~\ref{ssec:eql_semantics}. This is a deliberate choice: on a materialized knowledge base it answers questions that an open-world reasoner leaves undetermined, such as which students take at most one course.

\section{ORMatic: Long-Term Memory}
\label{sec:ormatic}

An agent also needs to keep knowledge beyond the lifetime of its process, for example as an episodic memory of what it has done~\cite{beetz2025robot}, and often more of it than fits in working memory. ORMatic is \ac{krrood}'s persistence layer and serves as the agent's long-term memory. From the same classes that form the TBox, it generates a relational schema and data access objects (DAOs) for SQLAlchemy, together with routines that convert objects to DAOs and back. The domain model therefore remains the single definition of the agent's knowledge: no separate schema has to be kept in sync with it, the domain classes remain free of persistence code, and mappings can be customized where the generated defaults do not fit. The database adds what working memory lacks for large amounts of data: indexes, a query optimizer that chooses how to evaluate each query~\cite{selinger1979access}, and tables that learning components can read directly.

\begin{lstlisting}[style=eql, float=t, caption={One \acs{eql} query evaluated in working memory and, translated by ORMatic, in long-term memory. The comment shows the essence of the generated SQL, which also joins the tables of the class hierarchy.}, label={lst:ormatic}]
s = variable(Student, domain=students)
older = an(entity(s).where(s.role_taker.has_age > 25))
in_memory = list(older.evaluate())              # working memory
stored = eql_to_sql(older, session).evaluate()  # long-term memory
# SELECT Student.* FROM Student JOIN Person
#   ON Person.id = Student.role_taker_id
#   WHERE Person.has_age > 25
\end{lstlisting}

Because an \ac{eql} query is a symbolic expression that is separate from its evaluation, the same query can be evaluated in working memory or translated to SQL and evaluated in the database (Listing~\ref{lst:ormatic}). The translator maps a variable to the table of its class and an attribute chain to joins. A collection-valued attribute, as every object property that Ontomatic generates is, is stored as rows of an association table: ranging over its elements becomes a join, and membership and existential quantification become correlated \texttt{EXISTS} subqueries. Universal quantification, predicates and functions, which run Python code, and rules, which create objects, are not translated; the translator rejects them instead of answering differently. On a test database over the part of the OWL2Bench model that the benchmark queries use, the translations of all 18 queries return the same answers as \ac{eql}. The SQL queries of our experiments (Section~\ref{sec:experiments}) were written by hand with SQLAlchemy.

\paragraph{Setup}
We use the OWL~2~RL profile of OWL2Bench~\cite{singh2020owl2bench} with one university: 3,667 individuals and 54,901 explicit statements. Its OWL~2~RL closure, computed by GraphDB, has 1,431,635 statements and serves as the pre-reasoned input. We run all 18 queries of the RL profile (Q2--5, Q7--16, Q19--22). The \ac{krrood} model is generated by Ontomatic from the ontology, in which we marked the classes that represent roles of a person or an organization with \texttt{roleFor} restrictions (Section~\ref{sec:ontomatic}). For the SQL queries, ORMatic persists the loaded objects in PostgreSQL, and the queries are written with SQLAlchemy over the generated schema.

We compare against four systems:
\begin{itemize}
  \item GraphDB 11.2 with the OWL~2~RL ruleset, in the free edition, which is limited to one CPU core;
  \item RDFLib 7.4 with the \texttt{owlrl} OWL~2~RL reasoner;
  \item Owlready2 0.49 with its bundled Pellet;
  \item Protégé 5.6.7 with Pellet.

\subsection{Correctness}
\label{ssec:correctness}

For every query, we normalized the answers of each system to a set of tuples of IRIs and literals and compared it with GraphDB's answer set. RDFLib, Owlready2, \ac{eql} and SQL over ORMatic return answer sets identical to GraphDB's on all 18 queries. Protégé's queries were run manually, and we did not compare its answer sets. Q9, Q13 and Q14 have empty answers in every system, because the RL ontology entails no instances for them. We also compared the knowledge base produced by Ontomatic with GraphDB's OWL~2~RL closure, assertion by assertion. For all 3,667 individuals, the 17,558 class memberships coincide: \ac{krrood} derives no class membership that the closure lacks and misses none. The same holds for the 1,385,869 object-property and the 20,933 data-property assertions. The check of Section~\ref{sec:ontomatic} finds no equality and no inconsistency, so on this knowledge base the unique-name assumption is entailed. This confirms Propositions~\ref{prop:soundness} and~\ref{prop:completeness} on the benchmark, to which they do not apply directly: OWL2Bench uses 47 IRIs both as classes and as individuals, and our \texttt{roleFor} markers lie outside OWL~2~RL, although they change no entailment, as every marked class is already a subclass of the marker's filler.

Q12 illustrates how roles reconcile OWL entailment with object types. In OWL2Bench, research groups have research projects, \texttt{hasResearchProject} is a sub-property of \texttt{hasWork}, and the domain of \texttt{hasWork} is \texttt{Employee}. The ontology therefore entails that every research group is an employee, and thus a person. A \texttt{ResearchGroup} object cannot become a \texttt{Person} by inheritance, so \ac{krrood} gives the research group's individual a second object, a \texttt{Person} with an \texttt{Employee} role. Q12 then returns the same 2,494 persons as GraphDB, while application code keeps a well-typed \texttt{ResearchGroup} object.

\section{Discussion and Conclusion}
\label{sec:discussion_conclusion}

We presented \ac{krrood}, which turns an agent's object-oriented program into its knowledge base. Property rules fire when application code asserts facts, class membership is derived when knowledge is loaded, and \ac{eql} queries the program under a closed-world semantics. Because the knowledge base is the program, application code reads and writes knowledge with ordinary attribute access, and axioms and rules can call the agent's own procedures. Ontomatic compiles OWL~2~RL ontologies into this form, and ORMatic stores the knowledge as long-term memory, which a subset of \ac{eql} can query through SQL. On OWL2Bench, \ac{krrood} returns the same answers as an OWL~2~RL reasoner on every query, its knowledge base equals the reasoner's closure assertion by assertion, and \tbd{} summary of cost.

\paragraph{Limitations}
\begin{itemize}
  \item \ac{krrood} adopts the closed-world and unique-name assumptions. It reports equal individuals but does not merge them, so facts that an equality propagates may be missing.
  \item Ontomatic targets OWL~2~RL. Constructs outside RL, and RL constructs that the generator does not compile, such as \texttt{oneOf}, are not supported.
  \item User-defined predicates and functions make \ac{eql} more expressive, but termination and complexity then depend on that code.
  \item Inferred facts are not retracted when the facts they were derived from are removed; incremental maintenance of materialized knowledge~\cite{MotikNenovPiroHorrocks2015} is future work.
  \item Negation as failure is evaluated over the derived facts, so where Ontomatic is incomplete, a closed-world answer can contradict OWL entailment.
  \item Materializing a rich object graph costs memory, and we evaluated a single benchmark scale.
\end{itemize}

\paragraph{Future work}
We will extend Ontomatic beyond OWL~2~RL towards OWL~DL constructs, and compile \ac{eql} conditions to Python so that axioms are evaluated in their declarative form at the speed of their compiled form. We also plan to evaluate \ac{krrood} as the belief base of agents that act on ontological knowledge, such as BDI agents.
