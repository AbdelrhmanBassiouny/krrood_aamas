Fix a semantic bug in EQL (krrood's Entity Query Language) in the cognitive_robot_abstract_machine repo at /home/bass/Projects/cognitive_robot_abstract_machine.

## Context
EQL is described in an AAMAS 2027 paper (deadline 8 Oct 2026) as having first-order semantics over finite, closed domains: `for_all(x, φ)` means ∀x ∈ D. φ, `exists(x, φ)` means ∃x ∈ D. φ, and `not_` is negation as failure. Here D may depend on outer bindings. The common case is a collection attribute of an outer variable, e.g. `c = flat_variable(s.takes_course)`, which should mean ∀c ∈ s.takes_course for EACH binding of s.

## Bug (reproduced on origin/main b0b59087a, 2026-10-05)
If the quantified variable's domain depends on an outer variable, the outer variable is quantified too: the condition is evaluated over the collections of ALL students instead of per student. `exists` happens to give the right answer, but `for_all` and `not_(exists(...))` do not.

```python
from __future__ import annotations
from dataclasses import dataclass, field
from krrood.entity_query_language.factories import an, entity, variable, flat_variable, for_all, exists, not_
from krrood.patterns.role import Role
from krrood.symbol_graph.symbol_graph import Symbol

@dataclass(eq=False)
class Course(Symbol):
    name: str

@dataclass(eq=False)
class Person(Symbol):
    name: str

@dataclass(eq=False)
class Student(Role[Person]):
    takes_course: set[Course] = field(default_factory=set)

logic, ai, dbs = Course("Logic"), Course("AI"), Course("Databases")
students = [Student(role_taker=Person("Alice"), takes_course={logic, ai}),
            Student(role_taker=Person("Bob"), takes_course={ai}),
            Student(role_taker=Person("Carol"), takes_course={logic, dbs})]

s = variable(Student, domain=students); c = flat_variable(s.takes_course)
# expected ['Alice', 'Bob']  -> actual []
an(entity(s).where(for_all(c, c.name != "Databases")))
s = variable(Student, domain=students); c = flat_variable(s.takes_course)
# expected ['Bob']           -> actual []
an(entity(s).where(not_(exists(c, c.name == "Logic"))))
s = variable(Student, domain=students); c = flat_variable(s.takes_course)
# expected ['Carol']         -> actual ['Carol'] (correct)
an(entity(s).where(exists(c, c.name == "Databases")))
s = variable(Student, domain=students); c = flat_variable(s.takes_course)
# expected all three         -> actual all three (correct)
an(entity(s).where(for_all(c, c.name != "Nope")))
```

## Second task (same branch, after the first is green): `match` on collection-valued attributes
In ontology-derived models (e.g. OWL2Bench, generated by Ontomatic), every non-functional object property is a set-valued attribute, such as `Student.takes_course: set[Course]`. Today a structural match on such an attribute silently returns nothing (reproduced on origin/main with the classes above):

```python
an(Student)(takes_course=logic).from_(students)                          # expected Alice, Carol -> actual []
an(Student)(takes_course=an(Course)(name="Databases")).from_(students)   # expected Carol       -> actual []
```

Wanted semantics (the same as a SPARQL triple pattern): for an attribute whose value is a collection, `attr=v` means v ∈ x.attr, and `attr=pattern` means ∃y ∈ x.attr such that y matches the pattern. Single-valued attributes keep equality. With this, the OWL2Bench query Q22 can be written as

```python
an(Student)(takes_course=an(Course)(is_taught_by=an(Person)(is_dean_of=an(Organization)())))
```
